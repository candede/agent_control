# Agent Control

## Quick Brief

This React client is built into the combined Agent Control Express artifact. The supported local workflow is the repository-root Docker deployment; there is no separate production frontend origin or host Node/Vite requirement.

## What This App Does

Agent Control presents saved, explicitly refreshed Microsoft Graph package observations and saved Power Platform inventory. Package list/detail reads use least-privileged delegated or separately approved application read access. Provider actions are capability-gated and never run on navigation.

Admins can use the app to:

- Sign in with a work or school account through Microsoft Entra ID.
- View authorized saved Copilot package observations.
- Search and filter agents by name, description, publisher, host, ID, or blocked state.
- Block or unblock a single Copilot agent.
- Select multiple agents and run bulk block or unblock actions.
- Inspect Available to and Installed for assignments when authorized.
- See package access controls disabled with the missing conditional-write protection explained.
- See owner reassignment disabled with its missing owner-readback/conditional-write contract and Microsoft documentation link.
- Review bulk action results, including succeeded, skipped, and failed packages.

The browser does not call Microsoft Graph directly. It calls the local Express backend, and the backend calls Microsoft Graph on behalf of the signed-in user.

## Requirements

Use the host and identity prerequisites in the [root runbook](../README.md): PowerShell 7, Docker with Compose v2, a browser, and an approved single-tenant Entra application's tenant ID, client ID and client secret for initial onboarding. An administrator must add the [required API permissions and grant admin consent](../docs/deployment-setup.md#api-permissions-administrator-prerequisite) before feature use. The app does not request feature grants. Microsoft Agent 365 licensing applies to package APIs.

## Run Locally

From the repository root:

```powershell
pwsh ./deploy-local.ps1 start
# Omitting start is equivalent:
pwsh ./deploy-local.ps1
```

The first or incomplete start prompts for tenant ID, client ID, hidden client secret and port (default `3001`). State is fixed at repository-root `.local/<lowercase-project>/`; there is no custom location. Use `pwsh ./deploy-local.ps1 start -Project newCustomer` to onboard or reuse `.local/newcustomer/`. Later starts reuse all saved values, including the port, without prompting. Open `http://localhost:<saved-port>` (default `http://localhost:3001`). Every `start` builds images, migrates, tests and starts the app. Build, test, lint, browser automation, Node and npm all run in Docker. The JSDOM suite uses at most two workers so the complete operator gate does not starve time-bound UI tests on shared machines; test assertions and deadlines remain unchanged.

The only public commands are positional `start` (default), `stop` and `edit-config`, plus `-Project` (default `agent-control`). `stop` preserves data and secrets. `edit-config` prompts for all four settings; Enter keeps each current value, and the current secret is never displayed. Unchanged settings are not rewritten and leave a running app untouched. Accepted client ID, client-secret or port changes safely stop the app and leave it stopped until an explicit `start`. A changed port requires the matching Entra Web callback `http://localhost:<saved-port>/api/auth/callback`. Input validation does not validate live credentials.

The tenant ID can change before a database volume exists, and a previously missing tenant ID can be filled in. Changing a nonempty saved tenant ID on an existing volume is rejected before stopping the app or writing settings. Edits do not migrate data between tenants; use a separate project for another tenant. See the [root runbook](../README.md) and [operator-only maintenance helpers](../docs/operations.md#operator-only-local-helpers) for recovery and isolated database tests.

Changing the saved client/application ID on an existing volume records `control/reauthenticate` while the app is stopped. The next `start` clears only persisted login sessions before reopening, requiring sign-in under the new app registration. The session-signing secret and all business data are preserved. Secret-only and port-only edits do not schedule this purge.

## How To Use The App

1. Open `http://localhost:<saved-port>` (default `http://localhost:3001`) and sign in when identity is configured.
2. Review **Permissions > App prerequisites**; an administrator configures any missing grants in the existing app registration, then you sign in again.
3. Explicitly refresh package observations; navigation itself never calls Microsoft Graph.
4. Search/filter saved rows and inspect package source, freshness, deployment, block state and assignments according to the current app role.
5. For block/unblock, review the exact targets and risk preview, confirm the change, then monitor the durable job and provider verification. No prior canary is required; current provider authorization remains enforced.
6. Reconcile an inconclusive item by read only; a new write always requires a new preview and confirmation.
7. Sign out when finished.

## Tables and server state

The workbench uses TanStack Query for passive saved-data reads and the installed TanStack Table v9 API for interactive list grids. The libraries are headless: existing semantic HTML, responsive table containers, detail dialogs and capability gates remain in place. No new runtime dependency is needed.

[SavedQueryProvider](src/components/SavedQueryProvider.tsx) scopes the shared client to the authenticated tenant, account, roles and session epoch. Sign-out, revalidation and account/role changes discard private queries. Standalone panels own an isolated client rather than a process-wide cache. [savedQueries](src/savedQueries.ts) provides a normal query hook and an observer-backed read adapter for workflows that already need generation fences, stale-snapshot warnings or bounded polling. Concurrent identical reads share a request, but cancelling one observer does not cancel another. Cancelling a shared query or clearing the client settles pending callers as cancelled; a reverted cached snapshot is never treated as a completed fresh read.

Saved reads have no automatic retry, focus/reconnect refetch or persistence; ordinary reads revalidate and unused results are garbage-collected immediately. The specialized Agents inventory cache retains its existing 30-second reuse window and checks source/report/person expiration before reuse. Mutation follow-up reads use action/revision keys or independent requests so they cannot join work admitted before the command, even when another observer keeps that earlier request alive. Initial report-admin metadata shares Query; explicit refresh and mutation verification use independent abortable GETs. Query keys include the applicable filters, page, snapshot, report and revision.

A scoped saved-Agents denial clears only that workspace's state and query families for the current principal. A separate agent epoch fences old reads, exports, mutations and callbacks even after recovery; unrelated report and Sync state survives. Session-wide authorization failures, including unreadable 401/403 responses, still clear the authenticated client and revalidate the session.

The **M365 Copilot licenses** view focuses on effective paid entitlement, not membership in a containing SKU such as E7. The default **Licensed users** cohort and all adoption cohorts/KPIs use the shared `isCopilotServiceActive` predicate: enabled, warning/grace and partially enabled qualify; disabled, suspended, locked-out and unknown do not. **Active M365 Copilot licensed users** still uses the authoritative backend `counts.licensedUsers`, including genuine zero and null, never a replacement calculated from roster size. Using agents, Needs attention and Agent usage unknown cover only effectively licensed users. The latter intentionally measures missing agent-report totals, independently of the backend's broader `unknownMetricsUsers` count that also considers app coverage.

The scope callout separately counts **directory users checked** from the complete saved candidate roster, not total tenant headcount. A successful available directory source establishes that all matching Graph pages and count checks completed for that saved tenant-wide filtered sync, not that every candidate is licensed. **All checked users** retains candidates for diagnostics, complete search/pagination and exact report joins. Stale, partial or failed-read records remain explicitly last saved with unverified styling; the default cohort may show last-known active records, but current counts and actionable adoption recommendations are withheld. Basic Copilot Chat access and usage are not measured and access can depend on policy. Neither absence of paid entitlement nor disabled paid features establishes that all Copilot or organizational/agent access is disabled.

[copilotServicePresentation](src/copilotServicePresentation.ts) supplies subordinate paid-feature labels: Active, Active (grace period), Not enabled, Suspended, Locked out, Unverified and Partially active. Grace-period and partially active users can still need follow-up; directory account sign-in status remains separate. Package/SKU names, assignment states and group provenance are not displayed; service enums and the API contract are unchanged.

**Reported activity** retains every imported identity, including concealed, unlinked and bridge-only users. Current license status requires a unique exact saved directory link with the same report set, Users version and Users & agents version, then applies the same effective-state rule to all candidates. Unmatched, ambiguous or stale identities remain **License not verified**, never inferred to be basic, unlicensed or disabled. Current entitlement proves neither activity nor historical coverage. The earlier service-schema upgrade's migration 37 remains historical, not a new reset requirement. Failed reads retain last-saved context without presenting it as current. The `licenses` route key is unchanged.

Power Platform ordering treats an absent environment as missing, not an empty name to sort first. Server filtering and ordering precede paging, with stable exact-identity ties. Restoring a quarantine selection requires every requested native ID to resolve uniquely in its authorized snapshot; matching only the number of returned rows is insufficient.

Inventory CSV and pagination require a successful read of the current saved-list query. Query, snapshot and revision changes cancel obsolete exports. Authorization is tracked per saved source: a denial clears that source's metadata and dependent actions without purging independently authorized results. Denied selections must revalidate before becoming actionable again. Refresh/resume responses cannot replace a newer exact-job selection or revive the same denied job, and duplicate in-flight commands are blocked.

Authentication, consent, provider permission checks, user-triggered directory searches/resolution, imports, downloads and confirmed mutations remain explicit API operations rather than cacheable queries. Existing foreground package/inventory/quarantine mutation-status loops and immediate provider readback also remain explicit: their freshness, cancellation, confirmation and time-budget contracts are not ordinary list caching. Directory searches and assignment resolution now abort superseded, disabled or unmounted requests. These choices do not introduce automatic provider collection or mutation retries.

Report confirmation errors stay inside the active dialog. Closing a pending deletion remains available; its later completion does not steal focus from another control. A denied parallel discard immediately clears that report-management workflow and fences late sibling results, without clearing unrelated provider scopes.

Jobs and Sync fence their affected metadata after authorization denial, including concurrent workspace and exact-run reads. Denied Jobs actions settle interrupted status indicators and leave Refresh status available for an explicit recheck without automatically restoring denied metadata. Refresh and action readbacks have observer-specific freshness epochs; recovery stays busy through the fresh status read. Actions from the full Jobs view also refresh the persistent saved Sync workspace, without submitting additional provider commands. Sync status polling continues across tab navigation without an elapsed-time cutoff. History keeps partial outcomes distinct from complete success, invalid or backwards timestamps remain unknown, and count sorting uses numeric values rather than localized labels such as `1,000`.

Investigation saved-read groups fail closed instead of combining a failed catalog/history/detail read with late sibling results. Unknown history counts are not zero, and stale selections cannot keep private evidence dialogs open. Scoped provider-consent failures remain distinct from saved-data authorization denial and do not clear unrelated queries. Passive history paging does not renew polling deadlines or attempt budgets; explicit refresh/actions can restart them. Qualification starts require valid future expiry, not merely a timestamp that fails to compare as expired. Explicit history refresh recovers saved reads; qualification, search, cancellation, deletion and export remain independently admitted actions. Local audit action filters round-trip through the URL, including report exports and Defender scope revocation.

Quarantine restoration cannot replace a newer action or clear a newer selection. Exact target tuples and saved-read revisions bind confirmations and activity to their original snapshot. Unlike report deletion, quarantine submission locks its confirmation until the response settles, retaining the frozen receipt and idempotency key for a safe retry; failures appear inside the dialog. A resume acknowledgement is followed by bounded current-job reads, not treated as proof that work has finished. Hidden or inactive assignment editors do not resolve directory principals.
