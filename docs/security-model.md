# Security model

Agent Control is a same-origin administrative application. The backend owns authentication, authorization, provider credentials, durable execution, and response filtering. Frontend checks improve the user experience but are not security boundaries.

## Identity and sign-in

- Microsoft Entra ID is the identity provider. Normal sign-in requests OIDC identity/refresh scopes and delegated directory scopes, with MSAL `extraScopesToConsent` for all implemented delegated capabilities, including `CopilotPackages.ReadWrite.All` and `CopilotStudio.AdminActions.Invoke`. This brings outstanding Graph and Power Platform consent into onboarding without mixing resource audiences in token acquisition. It requests no application permissions. Consent never bypasses the internal Admin role or exact-target confirmation required for writes. The explicit **Sign in without provider setup** path requests only `openid` and `profile`; role revalidation remains identity-only.
- Authorization code flow uses PKCE with `S256`, an OIDC nonce, and a process-local one-time transaction that expires after ten minutes. PostgreSQL receives only a random handle bound to the session; server-side state, nonce, and verifier are retained only in memory and transmitted only through the required Entra authorization/code exchange. The callback atomically consumes the transaction before processing provider errors or exchanging a code, so mismatch, expiry, and replay cannot redeem a code.
- The configured callback must share the application origin and use `/api/auth/callback`. Return targets must parse as same-origin paths; absolute, scheme-relative, backslash, and NUL-containing targets are rejected.
- Login establishes identity and app-role claims. Entra decides whether consent or additional interaction is necessary; the app neither forces consent on every recovery nor grants consent itself. Successful sign-in alone does not prove any provider operation, role, or license. Denied setup offers explicit retry or deferred setup without an automatic redirect loop.

## App roles

Agent Control has exactly two app-role values. Assign `AgentControl.Viewer` or `AgentControl.Admin` through the Enterprise application. One assignment is sufficient and recommended because Admin includes every Viewer permission. If direct and group membership overlap, holding both values is accepted and evaluates to the Admin superset; it does not create another role or authorization tier.

| Role | Authorized data and actions |
| --- | --- |
| `AgentControl.Viewer` | All read-only views, including broad inventory, exact targets and assignments, user-level accepted reports, security results, and local administrative audit. A Viewer may run, refresh, search, export, resume, and cancel their own delegated provider-read lifecycle; explicit Purview/Defender requests establish their own principal evidence. A Viewer cannot change provider state, write imports, change configuration, approve mutation or application/shared-scope qualification, or use mutation-job controls. |
| `AgentControl.Admin` | All Viewer access plus supported provider changes, imports, configuration, mutation and application/shared-scope approvals, mutation-job controls, and safe diagnostics. Capability-specific safety gates still apply. |

A recognized tenant user with no assigned current app role—including a user assigned only a disabled or legacy role—receives an authenticated shell and assignment diagnostics only. Protected data and mutations remain denied; roles are never inferred or auto-promoted.

The source boundary is enforced independently of those roles:

| Source / scope | `AgentControl.Viewer` | `AgentControl.Admin` |
| --- | --- | --- |
| Graph package inventory | All saved list/detail views, exact native targets and assignments; own delegated refresh/search/export jobs and cancellation | Same viewing plus on-demand confirmed package access/block changes and mutation-job controls |
| Power Platform inventory and quarantine | Initiating principal's snapshots, exact targets, status, counts and exports; own delegated read jobs and cancellation | Same principal-scoped viewing plus on-demand confirmed quarantine changes and mutation-job controls |
| Official usage reports | Tenant aggregate and user-level accepted projections and exports | Same viewing plus three-file validation, import, selection and deletion |
| Purview and Defender | Own explicit delegated searches and resulting private evidence/results; explicitly approved application-shared results; own exports and local cancellation/deletion; optional delegated qualification/retained-scope controls are not prerequisites for ordinary work | Same viewing plus application/shared-scope qualification and application-mode configuration |
| Local administrative audit and jobs | All authorized local audit views; own delegated read-job state and cancellation | Same viewing plus safe diagnostics and supported administrative/mutation job controls |

Every route declares access, roles and data class before its handler executes. Unregistered methods and routes fail closed. Repository predicates apply tenant, principal, token mode, result-scope configuration and selected snapshot before joins, counts, pages, detail lookup or export. Saved cache access never implies current provider permission, and current provider permission never widens saved-result scope.

Admin is a capability role, not a tenant-wide data bypass. Tenant, principal, source, token-mode, selected-snapshot, and retained-scope isolation remain in force. In particular, Admin cannot read another user's private delegated jobs or cached results merely because they are Admin.

App roles do not grant Microsoft provider permissions, consent, provider service access, licenses, or Microsoft tenant/provider roles. Optional application-mode capabilities require explicit Admin enablement, an approved shared scope, application permission qualification, and a registered adapter. There is no delegated-to-application fallback. Deployments that approve delegated access only must leave application mode disabled.

## Threat boundaries

- The browser and all supplied headers, paths, query values, multipart names, CSV cells and stored provider strings are hostile. React escaping, inert text rendering and formula-neutral CSV are defense in depth; Express policy and bounded repositories are authoritative.
- Express is the single public origin and owns OIDC, CSRF/origin checks, authorization, provider egress, projection and durable admission. It trusts one Azure proxy hop only on the Azure target and trusts no local forwarding header by default.
- Entra and the fixed Microsoft provider origins are external trust domains. A valid sign-in is not provider consent. OAuth state, nonce and PKCE bind a ten-minute one-use flow; audience/tenant/account/mode/permission checks bind each provider authorization.
- PostgreSQL is the only runtime persistence authority. `agentcontrol_app` can perform allowlisted runtime work and append audit but cannot own schema, assume `agentcontrol_admin`, mutate/truncate administrative audit, inspect migration receipts, or perform operator cleanup. A privileged database administrator can still alter ordinary audit: this design is append-only separation, not cryptographic tamper proof.
- The existing Key Vault is an administrator-prepared secret boundary. Six exact names are validated; only tenant ID, client ID, client secret, session secret and restricted runtime database password have App Service references. The database administrator password is bootstrap/operator-only and must be removed from short-lived deployment inputs after migration.
- Telemetry receives only allowlisted structured fields: bounded correlation IDs, provider/category, status, duration, age, attempt and count. The HTTP completion hook is installed before path validation, body parsing and request admission, so rejected parse and `429` outcomes are counted without recording the URL, query, headers or body. Tokens, cookies, codes, nonce/verifier values, claims, report rows, provider bodies, arbitrary errors and connection details are discarded. Azure diagnostic settings send only this console stream to the dedicated `AppServiceConsoleLogs` table plus aggregate metrics; raw App Service HTTP/IP/URL and PostgreSQL query/session/connection log categories are disabled. Alert queries parse the exact JSON `event` field rather than token-searching whole messages. Local `json-file` logs rotate at 10 MiB with three files per persistent service. There is no second telemetry stack.
- Official usage upload buffers and CSV export buffers are bounded process memory and are released after the request. Test scratch and package extraction are isolated Docker-run data and removed after checks. The runtime image has no writable upload volume and archives neither original filenames nor input bytes.
- Backups are operator-created restricted native dumps with a checksum and complete-table count/content fingerprint receipt. Version-3 receipts distinguish the database snapshot time from later dump completion so measured recoverable age starts at the truthful snapshot boundary. They are sensitive, expire after seven days locally, and provide no automatic cross-backup privacy suppression. Restore remains isolated and in database maintenance until session invalidation, ownership expiry, convergent retention and current deletion/access review complete.
- Operators and deployment identities are trusted for their explicit scope only. Cleanup requires the exact project/database confirmation and a dry-run option. Restore/reopen accepts only a new isolated database name. Azure deployment additionally requires a dated target, maintenance and budget approval; CLI login and example files are not approval.

The backend enforces route policy before handlers run and filters successful responses by data class. A route permission therefore cannot accidentally confer access to a more sensitive field class.

Delegated saved jobs and audit projections are tenant-scoped and private to their initiating principal. Application-mode enablement requires a separate explicit Admin approval for tenant-shared scope; it never converts private delegated results into shared data. Official Microsoft 365 usage reports are tenant-shared after an Admin accepts a compatible three-file set; Viewer and Admin can read both aggregate and user-level projections, while only Admin can manage imports and report-set selection. Filtering is enforced before joins, counts, pagination, retrieval and exports. Report agent IDs stay unresolved/report-only because no exact documented package equivalence exists; display names and creator strings cannot establish identity.

Official usage uploads are Admin-only multipart requests with CSRF/origin checks, an 8 MiB file limit, 50,000-row limit, bounded fields, two process-wide in-memory upload slots and a 15-second wall-clock deadline covering multipart parsing, report parsing and staging. Disconnect/deadline cancellation is propagated into repository work and rechecked before commit. An admission slot is not released until both parser and started repository work settle. The backend validates UTF-8 and CSV structure, rejects controls, duplicate identities, unsupported periods and schema drift, and releases raw buffers on every exit. Original bytes and filenames are never archived or logged. If cancellation cleanup cannot be verified, the response fails when possible and the service emits only a value-free cleanup event. One actor-owned bundle review hash covers all staged and retained companion intents; all three kinds publish in one tenant-serialized transaction or none do. A stale hash, revision change, bad companion, expiry, disconnect or wrong actor cannot replace the active set.

Accepted report rows are immutable content with independent 180-day expiry. Once a version is published, the runtime role cannot append another row to it. Atomic acceptance writes a separate content-free 180-day receipt bound to tenant, actor, bundle hash and expected revision; an exact retry returns its original result without replaying publication or changing selection. Staging expires after 30 minutes, is cleaned before admission and at startup/periodic maintenance, and cannot keep accepted content or its retry receipt alive. Minimal content-free import audit expires after 90 days. Deleting an active set clears selection without selecting an older set. Pseudonymous usernames are case-sensitive and scoped to report-set and version IDs; aggregate distinct-user values derive from exact dataset identities rather than adding per-agent counts. Creator type remains a report attribute with explicit source and cannot overwrite package or Power Platform authoring metadata.

The legacy browser key is detected only by enumerating key names; its value is never read. Every affected authenticated role receives the notice, but only Admin can submit a server-audited cleanup acknowledgement. Cleanup removes that exact key only after explicit discard or successful re-import acknowledgement and never runs on sign-out, unmount, cancellation or failure.

Power Platform refresh jobs, snapshots, filtered counts, details and exports apply tenant/principal scope before retrieval. Saved snapshots remain Viewer-accessible independently of current provider evidence. Exact source association never widens either source's visibility and never changes a package mutation target. It compares documented identifier kind and value within tenant and, for environment-scoped kinds, environment; names, owners, timestamps and same-value different-kind identifiers are not matches. Ambiguous and blueprint-parent relationships remain separate and visible.

Inventory association candidates come only from the selected current private snapshot, before page filtering, not the tenant-wide source identifier table or loaded browser packages. Missing required environment scope cannot establish identity, and resource IDs include their resource type. No currently documented package-to-Power-Platform equivalence is inferred. CSV cells neutralize formula prefixes. Inventory work revalidates the principal before dispatch and publication; account changes signal cancellation without waiting under the same account lock needed by publication. Shutdown separately drains all active work. No provider call starts from saved-data navigation or freshness timers.

## Sessions and role freshness

- Sessions are opaque, server-side PostgreSQL records addressed by an `HttpOnly` cookie with an eight-hour lifetime. HTTPS cookies are `Secure`; `SameSite=Lax` permits the Entra top-level GET callback.
- Only sanitized identity, recognized app roles, expiry metadata, CSRF state, authorization freshness metadata, and the random authentication-transaction handle are persisted. Access tokens, refresh tokens, ID tokens, authorization codes, OAuth state, OIDC nonces, PKCE verifiers, and MSAL cache contents are never stored in PostgreSQL or sent to the browser.
- MSAL's token cache remains process-local. A restart requires token reacquisition; persisted application data and sessions remain governed by their own expiry rules.
- The two-role application release treats legacy-role-only sessions as having no protected access; they are never upgraded or aliased. Deployment requires a fresh sign-in, and role-bound principal capability evidence is reacquired or revalidated under Viewer/Admin authority using existing session/account fencing. Migration 27 does not modify session or capability-cache tables.
- App roles are revalidated with Entra every five minutes. Revocation can therefore take up to that interval to affect an otherwise active session. Consent/account changes and logout are ordered against concurrent refreshes so stale role data cannot restore a revoked session.
- Logout evicts the account cache, pauses its delegated jobs, deletes all server-side sessions for that tenant/account, and expires the browser cookie.
- Power Platform role-template IDs are allowlisted from validated ID-token role claims into sanitized session state. Only the six documented inventory role IDs are retained; raw claims are not persisted. Full, AI-scoped and unknown coverage remain distinct.

## Browser mutation controls

- All authenticated state-changing API requests require a session-bound CSRF token in `X-CSRF-Token`.
- The backend also requires the request `Origin` to equal the configured application origin. Missing or mismatched `Origin` is rejected; there is no `Referer` fallback.
- App Service trusts exactly one reverse-proxy hop. Local deployments do not trust forwarding headers unless an operator explicitly sets `TRUST_PROXY=1` for a controlled proxy. The application origin is canonical and singular; wildcard origins and cross-origin API use are unsupported. Client-supplied identity headers never authenticate a caller.

### Permission Center

- The UI imports the backend capability types and renders only registered adapters. One shared gate explains backend decisions on provider actions and separately applies local data-role visibility. It does not infer grants, Microsoft roles, licenses or write qualification from a successful read.
- Expired or unavailable provider evidence affects evidence-backed controls without denying authorized saved data. On-demand Admin write controls do not require prior probe evidence; their submitted requests check actual provider authorization. When an authenticated assigned Viewer/Admin session appears, including after consent return, the UI loads `GET /api/capabilities` and immediately makes one `POST /api/capabilities/check`. The check repeats at the earliest delegated evidence expiry only while the document is visible; a hidden tab waits for visibility/focus. A fresh response with the same evidence signature but a later `expiresAt` renews the timer from that returned expiry.
- Exactly one frontend check promise runs per session generation. Both requests use `AbortSignal`; logout, unmount, or a tenant/principal/role change aborts and fences stale results. The ownership key is tenant plus principal plus sorted current roles. An expiry or transport failure receives exactly one delayed automatic retry after 30 seconds; after that, the failed evidence signature is remembered so timer, focus, StrictMode, and rendering cannot create another automatic retry for that signature.
- Consent rejects unregistered adapters. Provider callback failures consume the one-time flow before redirecting to a safe local path with a fixed cancellation, interaction-required or failed outcome. Provider error descriptions, OAuth state and token data are never reflected into UI notices.
- Interactive consent, MFA and Conditional Access cannot be automated away. A delegated `missing_permission` decision with the required internal role renders **Request consent**. `interaction_required` renders **Continue sign-in / consent** and explains that the required Microsoft interaction may include consent, MFA, or Conditional Access; it is not misclassified as missing permission. `authorization_expired` renders **Sign in again** without claiming missing permission or that new consent is required. Every action is explicit and scoped to that capability; none redirects automatically. Consent cancellation says **Consent was cancelled or denied. Existing permissions are unchanged.** Additional interaction says **Microsoft Entra requires further interaction or Conditional Access. Complete the required sign-in steps or contact your administrator.**
- Permission diagnostics expose only allowlisted error categories, bounded provider error codes, HTTP status and validated correlation identifiers, alongside code-owned requirements and observation timestamps. They never expose provider response bodies, token/claim data or another principal's evidence. A consent-required Entra suberror is not labeled expired authorization; generic `invalid_grant` requires interaction without asserting its cause.
- Browser qualification uses a separate Docker-only fixture app and isolated PostgreSQL databases. Test auth/provider mocks are not runtime routes or configuration options. Ordinary runtime validation rejects `AGENT_CONTROL_FIXTURE_MODE`, and production images contain neither the fixture runner nor browser/test dependencies. See the [qualification commands](../README.md#permission-center-qualification).

## Capabilities and provider credentials

- Side-effect-free `GET /api/capabilities` returns `{ value: CapabilityView[] }`. The authenticated assigned Viewer-accessible, CSRF-protected `POST /api/capabilities/check` accepts only an absent body or empty object and returns the same shape; Admin inherits Viewer access. Nonempty, array, and `null` bodies return `400 invalid_request` with **Automatic capability checks do not accept request parameters.** The frontend never calls it for unassigned or legacy-role-only sessions, and the backend never schedules page-load checks by itself. The CSRF-protected `POST /api/capabilities/:id/probe` remains an explicit targeted-retry API, not a UI prerequisite.
- Each `CapabilityView` contains its code-owned definition and decision, may carry application `configuration: { enabled, sharedDataScope }`, and includes an optional top-level `enabled` compatibility field. The backend currently emits `enabled` for every view, but consumers tolerate omission. The frontend uses it for application presentation and falls back to `configuration.enabled` for compatibility. `enabled` is false only for a disabled application capability; delegated and local capabilities report true. A disabled application capability is `not_configured` with `configuration.enabled=false`; an enabled but unapproved application capability remains `not_configured` with `configuration.enabled=true` and `sharedDataScope=false`. A decision contains `capabilityId`, `status`, `authorized`, `fresh`, optional `verification`, optional `checkedAt`, `expiresAt`, `lastSuccessAt`, optional allowlisted evidence `{ category?, correlationId?, httpStatus?, providerErrorCode? }`, remediation, and `previewQualification` (`not_required`, `unqualified`, or `qualified`). `authorized` is true only for `available`; evidence-backed decisions require unexpired evidence for `fresh`. An `on_demand` decision instead reports current Admin authorization with `fresh=true`, `previewQualification=not_required` and no evidence-expiry requirement: provider authorization is checked when the operation runs. Verification values are `token`, `provider`, `local`, `on_demand`, or `qualification`. `on_demand` is not token or live-operation proof; qualification records separately verified optional evidence, never an ordinary-write prerequisite. Failed, unchecked, disabled and expired provider checks carry no successful verification claim. The UI also guards older payloads so a probe type cannot be mistaken for successful proof.
- Provider statuses are `available`, `missing_permission`, `missing_internal_role`, `missing_role`, `missing_license`, `not_configured`, `unsupported`, `preview_disabled`, `provider_error`, and `unknown`. `interaction_required` and `authorization_expired` are evidence categories, not additional capability statuses: their decisions map to `unknown` while preserving the exact safe category. The UI consumes those categories to render the applicable sign-in or consent action. A confirmed missing grant remains status/category `missing_permission`; ambiguous `401`/`403` and source failures map to `provider_error`, while explicit unsupported or `404` responses map to `unsupported`. Correlation IDs are sanitized, and bearer data/provider bodies are stripped.
- Capability definitions are code-owned contracts. Admins can configure application-mode enablement and approved shared scope. Automatic and explicit delegated checks are non-mutating and session-scoped; neither accepts fabricated evidence or edits provider, audience, permissions, roles, or write qualification.
- Package access, block/unblock and Copilot Studio quarantine management use `on_demand` probing. Ordinary Admin-confirmed writes require no prior canary or qualification record. Token/status readiness is not exact-target operation proof; current provider authorization, exact targets, immediate prestate checks and readback are enforced by the submitted operation.
- Provider permission is acquired only for the capability that needs it. OIDC login scopes, delegated capability scopes, and application-role capability permissions are separate authorization paths.
- Microsoft access tokens are client-opaque. The runtime validates MSAL response tenant, account, token mode, returned delegated scopes or exposed application roles, resource metadata when exposed, and expiry. Optional readable JWT claims can reject contradictions, but the client does not require Microsoft-owned access tokens to be parseable JWTs.
- Provider-read evidence is keyed by tenant, resource principal/application, authorizing principal, capability, resource audience, environment, token mode, permission revision, contract revision, and configuration revision. Full check batches are singleflight by tenant/principal/generation/effective Admin access/retry mode, individual refreshes are singleflight by evidence key, and fresh successes or failures are reused during the five-minute cooldown. A concurrent Viewer batch cannot suppress Admin-only token checks. Automatic, targeted-refresh, and read-through paths capture the generation before any await. Invalidation during configuration, token, or provider work prevents later provider steps and evidence publication. Successful login/consent plus logout or demotion invalidation increments the generation and deletes that principal's evidence. A generation change fails with `401 authorization_expired` rather than returning stale or mixed results. Each coalesced caller receives a separate current-role projection, preventing an Admin-shaped response from leaking to a Viewer.
- Evidence expires after five minutes and immediately stops authorizing access, but the expired row remains available as stale diagnostic metadata until explicit operator retention removes it. Safe checks separately bound token acquisition to ten seconds and provider reads to ten seconds, except the first-page package catalog check has a thirty-second provider budget (at most forty seconds including token acquisition). Catalog response bodies share that abort signal and retain the two-MB limit; no undocumented row-limit query is added. The fixed eligible set runs concurrently. Eligible explicit delegated operations perform one read-through refresh when readiness evidence is absent or expired, so a manual probe is never required.
- Ordinary catalog, directory and inventory checks may invoke their bounded safe read adapter. Authorized quarantine read, Purview, Defender and implemented Admin write checks acquire only the scoped delegated token; token success is not proof that an exact provider operation, tenant data source or license is available. Package access/block and quarantine management initially report `on_demand` Admin authorization only when no evidence exists. Automatic checks replace this with expiring `token` evidence or a failure; on-demand readiness never overrides missing permission, interaction errors or expired evidence. The submitted operation still acquires and validates provider authorization. Viewer receives `missing_internal_role`. Management availability selects no target, calls no quarantine status or mutation, executes/resumes/reconciles no job, and runs no canary.
- Automatic checks never include application/shared mode, imports, provider writes, mutation canary execution, raw-data collectors, Audit Search or Defender workloads, or data-refresh jobs. Disabled optional application modes are excluded from primary health, remain Admin-configured, and are never used as delegated fallback. The separate Agents initial-inventory workflow can submit one delegated read-only refresh per authorized session when no broad saved snapshot exists; a Permissions first-page check alone does not import inventory.
- Token-only availability is labeled **Ready to try** and explains **Token acquired. Ready to try; provider role, license, and operation access have not been verified.** Provider verification explains **The bounded provider request succeeded. Documented role and license metadata are not independently verified.** Local verification explains **Authorized by current local application policy.** Omitted compatibility verification may allow an otherwise authorized fresh read, but the UI explains **Authorization is available, but the verification level was not reported.** and counts it degraded, never verified. On-demand writes require current Admin authority and acquire/check delegated provider authorization when submitted; they need neither qualification provenance nor a prior token-readiness check. On-demand availability is not a claim that any provider request succeeded. Unknown unchecked, stale, and provider-error explanations distinguish pending checks and preserved saved-data access from proven missing permissions.
- Primary health excludes disabled application-mode rows and renders `<n> verified / <n> ready to try / <n> degraded / <n> blocked`, **Checking permissions** while pending, or **Permission status unavailable** after transport failure. Once an application mode is enabled, it participates normally; enabled but shared-scope-unapproved mode is degraded/not-configured rather than excluded. Inactive application rows are collapsed under **Optional shared application modes** and explicitly described as unnecessary for delegated installation. The normal UI recovery is top-level **Check status**, which reruns GET then the bounded POST with `?retry=failed` and reads **Checking...** while active. This explicit mode retries failed eligible delegated checks even when their diagnostic evidence is fresh, but reuses current successes and active provider-throttling cooldowns. Automatic checks retain the default fresh-evidence reuse; both modes coalesce equivalent in-flight probes and never select application capabilities or preview writes. The targeted probe API remains available without restoring a per-row UI ritual.
- On-demand decisions display **Ready to try** with verification metadata **Ready to try; Microsoft validates permission on the actual operation**. The explanation asks the Admin to review and confirm exact targets and states that Microsoft validates delegated permissions/provider roles on the actual operation. Token-ready and on-demand decisions both count as ready to try, never provider-verified.
- Exact remediation remains code-owned: interaction requires **Sign in again or complete delegated consent before retrying.**; expired authorization requires **Sign in again before retrying.**; Audit unknown requires **Run the automatic delegated readiness check or submit one explicit bounded search.**; Defender unknown requires **Run the automatic delegated readiness check or submit one explicit bounded investigation.**; generic provider error requires **Retry the bounded probe; an ambiguous provider failure does not identify a missing role or license.**
- Azure runtime configuration uses five native Key Vault references: tenant ID, client ID, client secret, session secret, and the restricted application database password. The separate PostgreSQL administrator password is available only to provisioning, migrations, and operator maintenance.
- Provider URLs and pagination links are parsed and checked against the expected HTTPS origin and route family before an authorization header is attached. Redirects are rejected. These checks prevent hostile configuration or provider links from forwarding bearer credentials to another host.

## Durable jobs

Durable jobs persist immutable business intent, exact targets, capability ID, tenant/principal identity, token mode, status, bounded attempts, leases, deadlines, and sanitized results. They do not persist provider tokens or use saved requester roles as execution authority.

Immediately before each unsent provider write, including explicitly resumed work after restart, the worker reacquires authorization and rechecks:

1. the current capability policy against freshly revalidated requester roles;
2. the capability's current enabled and availability state; and
3. the ability to acquire fresh provider authorization for the exact tenant/account, resource, mode, and grant.

The token returned by that final check is the token used for the write. A capability disabled after enqueue, removed authorization, or unavailable credential returns unsent work to `waiting_authorization`; a provider 401/403 on the pre-write read does the same. Once an attempt is marked sent, an uncertain outcome remains inconclusive and requires reconciliation, including a write-response 401/403. No completed or uncertain provider write is retried. Dispatch has a finite 30-minute deadline and jobs expire after seven days.

Power Platform refresh jobs are a separate read-only lifecycle. Submission records immutable principal/role/environment/type/query intent before work. A current capability decision and process-local delegated token are required before `running`; page/count progress is safe metadata, while resource rows publish atomically only after complete paging. Provider/schema/limit failure preserves the previous snapshot. Shutdown aborts in-flight reads and returns them to `waiting_authorization`; startup performs that state conversion only and never calls a provider. There is no scheduler, navigation-triggered fetch, application-token substitution or raw-response persistence.

Package inventory uses its own read-only refresh jobs and principal-scoped complete observations. Opening Agents starts at most one initial delegated refresh per account/UI session after a successful saved-data read returns `snapshot: null` and discovery finds no existing refresh jobs or prior attempt/success metadata. Otherwise list/detail navigation reads PostgreSQL without acquiring a provider token. Existing or failed work requires explicit Refresh or resume, not automatic replay. Opening the access editor explicitly refreshes the exact package read-only and fetches current details; bulk access preparation refreshes each selected target before confirmation. These reads do not replace dispatch-time prestate checks or perform writes. A delegated inventory refresh requires `CopilotPackages.Read.All`; separately enabled application refresh requires an Admin-approved shared scope. Partial, failed, interrupted or expired scans do not replace the last complete broad observation.

Purview Audit Search is a separate on-demand provider-read lifecycle. Viewer may submit and access their own delegated results without a separate qualification approval/start ritual; the explicit bounded search establishes evidence for that principal and request. Admin inherits that workflow and adds application/shared-scope qualification and configuration but does not gain access to another principal's private results. Application results are readable only through the current Admin-approved shared scope and exact application qualification. The runtime accepts only code-owned presets, required operation subsets and structured filters, persists a durable operation marker before create, never retries an ambiguous POST, and requires explicit current authorization to reconcile or poll after interruption. Every physical Graph attempt reserves durable capacity immediately before dispatch; provider and local request IDs remain separate, and execution owner/version fencing prevents stale publication. Automatic capability checks acquire a token but perform zero Graph query operations. Cancellation and deletion are local only; Microsoft may continue remote work. Stored rows are allowlisted metadata with message IDs but no prompt, response, transcript or unrestricted `auditData`. Results expire after 30 days, remain separate from local administrative audit and official usage, and associate with private Power Platform inventory only through exact Bot ID plus environment. See [the Audit Search runbook](purview-audit-search.md).

Every available package mutation requires a current server preview hash over the actor, exact native targets, frozen mutation-relevant prestate and requested intent. Jobs retain that summary and per-target prestate immutably. A tenant/package advisory lock serializes this application's local operations; under it the worker immediately rereads and hashes provider state before dispatch. Microsoft documents no ETag/`If-Match` on these endpoints, so this cannot prevent an external administrator from changing state after the reread and is never represented as provider atomicity. Full access replacement can overwrite such a concurrent change even though the app preserves and verifies the unselected collection. This risk is disclosed, not used to withhold implemented access or block/unblock functionality. Duplicate, non-UUID, unresolved, deleted or redirected principals are rejected.

Implemented Admin package access, block/unblock and quarantine operations run on demand without prior canaries, qualification records, or extra configuration in any deployment. Authentication, Admin revalidation, Microsoft delegated authorization, CSRF, exact targets, frozen intent, immediate prestate checks, audit, one-shot dispatch and readback remain enforced. Optional canaries retain their actual approval/restoration rules without gating ordinary operations. Owner reassignment has no implemented product workflow or documented owner readback. Application/shared modes retain their separate configuration and scope requirements.

Package mutation dispatch is one-shot. Bounded detail reads must observe the expected semantic state before success; HTTP `204` is only acceptance. Timeout or ambiguous state after dispatch is durable `inconclusive`. Reconciliation acquires current Admin identity and delegated package-read authority before each target and before publishing its result, honors cancellation, and performs provider reads only; it can mark an operation observed-applied, observed-not-applied/retry-eligible, or conflicting, but never automatically retries a mutation or depends on an unexpired write qualification.

Optional write qualification is separate from read evidence and ordinary write authorization. An Admin creates a 30-minute typed approval and a different Admin principal claims it once with current code-derived contract/configuration/delegated-auth identity. Attempted evidence has 30-day retention. The restoration service stores no token, stops before writing on intervening state, dispatches once, and qualifies only after exact semantic read-back; unknown state/criteria keys are never accepted from callers. A full block canary records both directional outcomes. A changed contract/configuration/auth mode or expired approval prevents that canary execution/publication, not ordinary Admin-confirmed writes. The restoration and intervening-change stop rules are defined in [mutation-canaries.md](mutation-canaries.md).

## Audit and residual risk

Durable-operation requested, started, skipped, succeeded, failed, inconclusive and provider-verified outcomes use the existing append-only audit service with exact target, actor, operation/job/correlation identifiers and minimal before/after evidence. Capability configuration records the updating principal/revision; probe evidence retains only allowlisted diagnostic fields. Provider tokens, provider response bodies and unnecessary principal attributes are excluded from persisted diagnostics. This is ordinary local audit, not a hash chain or external checkpoint service.

Residual risks include the configured role-revalidation delay, process-local token-cache loss on restart, upstream provider/API changes, preview connector/capability-detail fields, Resource Query availability differences outside global cloud, classic/V1 bot exclusion, unpublished configuration omissions, hidden workflow environments, Azure Resource Manager Conditional Access dependencies, and the operator's responsibility to assign Entra roles correctly. No live Power Platform tenant was available for this phase, so local tests qualify bounds and failure behavior but do not claim consent, role, cloud or tenant-data success.

## Transport, admission and recovery

Production serves one HTTPS origin with HSTS for one year including subdomains, CSP limited to self (with inline CSS only), frame denial, `nosniff`, no-referrer and disabled camera/microphone/geolocation/payment/USB. Local HTTP intentionally omits HSTS. API, HTML and deep links are `no-store`; content-hashed assets are immutable for one year. API JSON is limited to 512 KiB. Provider clients use fixed HTTPS origins, manual redirect rejection, bounded pages/rows/bytes and deadlines.

One process admits at most 1,200 read or 300 write API requests per minute per trusted IP and 600 read or 200 write requests per minute per authenticated principal. Liveness, readiness and auth status are excluded. The limiter holds at most 10,000 local keys and is intentionally not a distributed quota. Uploads allow two concurrent 8 MiB/50,000-row operations. Exports have source-specific row/byte ceilings and a 15-second publication deadline. Provider workers and durable queues retain their smaller per-principal, attempt, page and concurrency bounds; durable database admission, leases and one-shot dispatch survive process restart.

The singleton database operational state is runtime-readable but operator-writable. Readiness fails for missing/changed schema, maintenance file or database maintenance mode. Safe Admin diagnostics reveal only auth configuration, maintenance/provider admission state, schema version and fixed pool/body/export limits. Optional provider failure disables its capability rather than liveness. A logical restore migrates only a known schema prefix, verifies receipt fingerprints, invalidates sessions, staging previews, confirmations and provider qualifications, fences old ownership, marks sent writes inconclusive, and repeats bounded retention to zero before review. It compares exact current owners and authority bindings for retained caches, current official set/version deletion and selection, and Defender retained-scope revocation. Reopening repeats that comparison from one current-database snapshot while holding the restored operational row in a real transaction; unavailable or over-bound current review fails closed in maintenance. Mismatched cached content is purged, provider work remains disabled, and uncertain writes are never replayed.
