# Security model

Agent Control is a same-origin administrative application. The backend owns authentication, authorization, provider credentials, durable execution, and response filtering. Frontend checks improve the user experience but are not security boundaries.

## Identity and sign-in

- Microsoft Entra ID is the identity provider. Initial sign-in requests only `openid` and `profile`; provider permissions are not part of login.
- Authorization code flow uses PKCE with `S256`, an OIDC nonce, and a process-local one-time transaction that expires after ten minutes. PostgreSQL receives only a random handle bound to the session; server-side state, nonce, and verifier are retained only in memory and transmitted only through the required Entra authorization/code exchange. The callback atomically consumes the transaction before processing provider errors or exchanging a code, so mismatch, expiry, and replay cannot redeem a code.
- The configured callback must share the application origin and use `/api/auth/callback`. Return targets must parse as same-origin paths; absolute, scheme-relative, backslash, and NUL-containing targets are rejected.
- Login establishes identity and app-role claims. It does not imply a provider capability or provider consent.

## Independent app roles

The four app roles are independent. None inherits access from another, including `AgentControl.Administrator`.

| Role | Authorized data and actions |
| --- | --- |
| `AgentControl.Reader` | Broad package inventory, principal-private saved Power Platform inventory, package summaries, and aggregate reports. Exact user/group assignment arrays are removed from package-detail responses. |
| `AgentControl.Operator` | Exact-target package reads needed for an operation, exact user/group resolution, qualified package block controls, read-only reconciliation, and durable operation status. Access replacement and reassignment remain disabled by operation-specific safety gates. It does not grant aggregate reports, user-identifying reports, security records, imports, or capability administration. |
| `AgentControl.SecurityReader` | User-identifying usage/report rows, users, audit data, and security investigation results. It does not grant package mutation or capability administration. |
| `AgentControl.Administrator` | Capability configuration, report import/validation preview, and administrative metadata. It does not automatically grant Reader, Operator, or SecurityReader access. |

A recognized tenant user with no assigned app role receives an authenticated shell and assignment diagnostics only. Protected data and mutations remain denied.

The source boundary is enforced independently of those roles:

| Source / scope | Reader | Operator | SecurityReader | Administrator |
| --- | --- | --- | --- | --- |
| Graph package inventory | Broad tenant/principal observation; assignment arrays omitted | Exact native targets needed by an operation; qualified mutation only | Denied | Denied |
| Power Platform inventory | Initiating principal's saved snapshots, counts and exports | Exact quarantine target status only; no broad inventory | Denied | Import/capability metadata only |
| Official usage reports | Tenant aggregate projection/export | Denied | Tenant user projection/export | Three-file validation preview and import metadata, not accepted report rows |
| Purview/Defender/local administrative audit | Denied | Own operation/job status only | Delegated private or explicitly approved application scope plus administrative audit | Qualification/configuration and safe diagnostics only |

Every route declares access, roles and data class before its handler executes. Unregistered methods and routes fail closed. Repository predicates apply tenant, principal, token mode, result-scope configuration and selected snapshot before joins, counts, pages, detail lookup or export. Saved cache access never implies current provider permission, and current provider permission never widens saved-result scope.

## Threat boundaries

- The browser and all supplied headers, paths, query values, multipart names, CSV cells and stored provider strings are hostile. React escaping, inert text rendering and formula-neutral CSV are defense in depth; Express policy and bounded repositories are authoritative.
- Express is the single public origin and owns OIDC, CSRF/origin checks, authorization, provider egress, projection and durable admission. It trusts one Azure proxy hop only on the Azure target and trusts no local forwarding header by default.
- Entra and the fixed Microsoft provider origins are external trust domains. A valid sign-in is not provider consent. OAuth state, nonce and PKCE bind a ten-minute one-use flow; audience/tenant/account/mode/permission checks bind each provider authorization.
- PostgreSQL is the only runtime persistence authority. `agentcontrol_app` can perform allowlisted runtime work and append audit but cannot own schema, assume `agentcontrol_admin`, mutate/truncate administrative audit, inspect migration receipts, or perform operator cleanup. A privileged database administrator can still alter ordinary audit: this design is append-only separation, not cryptographic tamper proof.
- The existing Key Vault is an administrator-prepared secret boundary. Six exact names are validated; only tenant ID, client ID, client secret, session secret and restricted runtime database password have App Service references. The database administrator password is bootstrap/operator-only and must be removed from short-lived deployment inputs after migration.
- Telemetry receives only allowlisted structured fields: bounded correlation IDs, provider/category, status, duration, age, attempt and count. The HTTP completion hook is installed before path validation, body parsing and request admission, so rejected parse and `429` outcomes are counted without recording the URL, query, headers or body. Tokens, cookies, codes, nonce/verifier values, claims, report rows, provider bodies, arbitrary errors and connection details are discarded. Azure diagnostic settings send only this console stream to the dedicated `AppServiceConsoleLogs` table plus aggregate metrics; raw App Service HTTP/IP/URL and PostgreSQL query/session/connection log categories are disabled. Alert queries parse the exact JSON `event` field rather than token-searching whole messages. Local `json-file` logs rotate at 10 MiB with three files per persistent service. There is no second telemetry stack.
- Official usage upload buffers and CSV export buffers are bounded process memory and are released after the request. Test scratch and package extraction are isolated Docker-run data and removed after checks. The runtime image has no writable upload volume and archives neither original filenames nor input bytes.
- Backups are operator-created restricted native dumps with a checksum and complete-table count/content fingerprint receipt. Version-3 receipts distinguish the database snapshot time from later dump completion so measured recoverable age starts at the truthful snapshot boundary. They are sensitive, expire after seven days locally, and provide no automatic cross-backup privacy suppression. Restore remains isolated and in database maintenance until session invalidation, ownership expiry, convergent retention and current deletion/access review complete.
- Operators and deployment identities are trusted for their explicit scope only. Cleanup requires the exact project/database confirmation and a dry-run option. Restore/reopen accepts only a new isolated database name. Azure deployment additionally requires a dated target, maintenance and budget approval; CLI login and example files are not approval.

The backend enforces route policy before handlers run and filters successful responses by data class. A route permission therefore cannot accidentally confer access to a more sensitive field class.

Delegated saved jobs and audit projections are tenant-scoped and private to their initiating principal. Application-mode enablement requires a separate explicit administrator approval for tenant-shared scope; it never converts private delegated results into shared data. Official Microsoft 365 usage reports are tenant-shared after an Administrator accepts a compatible three-file set: Reader receives aggregate projections only, SecurityReader receives user-level projections, and Administrator receives operational import metadata without report content. Filtering is enforced before joins, counts, pagination, retrieval and exports. Report agent IDs stay unresolved/report-only because no exact documented package equivalence exists; display names and creator strings cannot establish identity.

Official usage uploads are Administrator-only multipart requests with CSRF/origin checks, an 8 MiB file limit, 50,000-row limit, bounded fields, two process-wide in-memory upload slots and a 15-second wall-clock deadline covering multipart parsing, report parsing and staging. Disconnect/deadline cancellation is propagated into repository work and rechecked before commit. An admission slot is not released until both parser and started repository work settle. The backend validates UTF-8 and CSV structure, rejects controls, duplicate identities, unsupported periods and schema drift, and releases raw buffers on every exit. Original bytes and filenames are never archived or logged. If cancellation cleanup cannot be verified, the response fails when possible and the service emits only a value-free cleanup event. One actor-owned bundle review hash covers all staged and retained companion intents; all three kinds publish in one tenant-serialized transaction or none do. A stale hash, revision change, bad companion, expiry, disconnect or wrong actor cannot replace the active set.

Accepted report rows are immutable content with independent 180-day expiry. Once a version is published, the runtime role cannot append another row to it. Atomic acceptance writes a separate content-free 180-day receipt bound to tenant, actor, bundle hash and expected revision; an exact retry returns its original result without replaying publication or changing selection. Staging expires after 30 minutes, is cleaned before admission and at startup/periodic maintenance, and cannot keep accepted content or its retry receipt alive. Minimal content-free import audit expires after 90 days. Deleting an active set clears selection without selecting an older set. Pseudonymous usernames are case-sensitive and scoped to report-set and version IDs; aggregate distinct-user values derive from exact dataset identities rather than adding per-agent counts. Creator type remains a report attribute with explicit source and cannot overwrite package or Power Platform authoring metadata.

The legacy browser key is detected only by enumerating key names; its value is never read. Every affected authenticated role receives the notice, but only Administrator can submit a server-audited cleanup acknowledgement. Cleanup removes that exact key only after explicit discard or successful re-import acknowledgement and never runs on sign-out, unmount, cancellation or failure.

Power Platform refresh jobs, snapshots, filtered counts, details and exports apply tenant/principal scope before retrieval. Saved snapshots remain Reader-accessible independently of current provider evidence. Exact source association never widens either source's visibility and never changes a package mutation target. It compares documented identifier kind and value within tenant and, for environment-scoped kinds, environment; names, owners, timestamps and same-value different-kind identifiers are not matches. Ambiguous and blueprint-parent relationships remain separate and visible.

Inventory association candidates come only from the selected current private snapshot, before page filtering, not the tenant-wide source identifier table or loaded browser packages. Missing required environment scope cannot establish identity, and resource IDs include their resource type. No currently documented package-to-Power-Platform equivalence is inferred. CSV cells neutralize formula prefixes. Inventory work revalidates the principal before dispatch and publication; account changes signal cancellation without waiting under the same account lock needed by publication. Shutdown separately drains all active work. No provider call starts from saved-data navigation or freshness timers.

## Sessions and role freshness

- Sessions are opaque, server-side PostgreSQL records addressed by an `HttpOnly` cookie with an eight-hour lifetime. HTTPS cookies are `Secure`; `SameSite=Lax` permits the Entra top-level GET callback.
- Only sanitized identity, recognized app roles, expiry metadata, CSRF state, authorization freshness metadata, and the random authentication-transaction handle are persisted. Access tokens, refresh tokens, ID tokens, authorization codes, OAuth state, OIDC nonces, PKCE verifiers, and MSAL cache contents are never stored in PostgreSQL or sent to the browser.
- MSAL's token cache remains process-local. A restart requires token reacquisition; persisted application data and sessions remain governed by their own expiry rules.
- Legacy role-less session records are deleted at first use. They are not upgraded optimistically.
- App roles are revalidated with Entra every five minutes. Revocation can therefore take up to that interval to affect an otherwise active session. Consent/account changes and logout are ordered against concurrent refreshes so stale role data cannot restore a revoked session.
- Logout evicts the account cache, pauses its delegated jobs, deletes all server-side sessions for that tenant/account, and expires the browser cookie.
- Power Platform role-template IDs are allowlisted from validated ID-token role claims into sanitized session state. Only the six documented inventory role IDs are retained; raw claims are not persisted. Full, AI-scoped and unknown coverage remain distinct.

## Browser mutation controls

- All authenticated state-changing API requests require a session-bound CSRF token in `X-CSRF-Token`.
- The backend also requires the request `Origin` to equal the configured application origin. Missing or mismatched `Origin` is rejected; there is no `Referer` fallback.
- App Service trusts exactly one reverse-proxy hop. Local deployments do not trust forwarding headers unless an operator explicitly sets `TRUST_PROXY=1` for a controlled proxy. The application origin is canonical and singular; wildcard origins and cross-origin API use are unsupported. Client-supplied identity headers never authenticate a caller.

### Permission Center

- The UI imports the backend capability types and renders only registered adapters. One shared gate explains backend decisions on provider actions and separately applies local data-role visibility. It does not infer grants, Microsoft roles, licenses or write qualification from a successful read.
- Expired or unavailable provider evidence disables provider controls without denying authorized saved data. Permission navigation, current-account probe requests and role-authorized consent remain independent of provider availability. No navigation or expiry timer launches a provider probe; catalog refresh is explicit.
- UI evidence is isolated to the loaded account and discarded from display immediately on account changes. Pending responses are generation-fenced. This is defense in depth; server route policies and tenant/principal repository scopes remain authoritative.
- Consent rejects unregistered adapters. Provider callback failures consume the one-time flow before redirecting to a safe local path with a fixed cancellation, interaction-required or failed outcome. Provider error descriptions, OAuth state and token data are never reflected into UI notices.
- Permission diagnostics expose only allowlisted error category and validated correlation identifier, alongside code-owned requirements and observation timestamps. They never expose provider response bodies or another principal's evidence.
- Browser qualification uses a separate Docker-only fixture app and isolated PostgreSQL databases. Test auth/provider mocks are not runtime routes or configuration options. Ordinary runtime validation rejects `AGENT_CONTROL_FIXTURE_MODE`, and production images contain neither the fixture runner nor browser/test dependencies. See the [qualification commands](../README.md#permission-center-qualification).

## Capabilities and provider credentials

- Capability definitions are code-owned contracts. Administrators can configure application-mode enablement and approved shared scope; authenticated callers can request their own non-mutating probes. Neither route accepts fabricated evidence or edits provider, audience, permissions, roles, or write qualification.
- Missing configuration, role assignment, evidence, or preview qualification produces the corresponding registry status, such as `not_configured`, `missing_internal_role`, `unknown`, or `preview_disabled`. `unavailable` is not a registry status.
- Provider permission is acquired only for the capability that needs it. OIDC login scopes, delegated capability scopes, and application-role capability permissions are separate authorization paths.
- Microsoft access tokens are client-opaque. The runtime validates MSAL response tenant, account, token mode, returned delegated scopes or exposed application roles, resource metadata when exposed, and expiry. Optional readable JWT claims can reject contradictions, but the client does not require Microsoft-owned access tokens to be parseable JWTs.
- Provider-read evidence is keyed by tenant, resource principal/application, authorizing principal, capability, resource audience, environment, token mode, permission revision, contract revision, and configuration revision. Same-key probes share one in-flight request; consent, role, or configuration invalidation fences stale completions. Persisted details are an allowlist of static contract/category and validated correlation ID only.
- Evidence expires after five minutes and immediately stops authorizing access, but the expired row remains available as stale diagnostic metadata until explicit operator retention removes it.
- Azure runtime configuration uses five native Key Vault references: tenant ID, client ID, client secret, session secret, and the restricted application database password. The separate PostgreSQL administrator password is available only to provisioning, migrations, and operator maintenance.
- Provider URLs and pagination links are parsed and checked against the expected HTTPS origin and route family before an authorization header is attached. Redirects are rejected. These checks prevent hostile configuration or provider links from forwarding bearer credentials to another host.

## Durable jobs

Durable jobs persist immutable business intent, exact targets, capability ID, tenant/principal identity, token mode, status, bounded attempts, leases, deadlines, and sanitized results. They do not persist provider tokens or use saved requester roles as execution authority.

Immediately before each unsent provider write, including explicitly resumed work after restart, the worker reacquires authorization and rechecks:

1. the current capability policy against freshly revalidated requester roles;
2. the capability's current enabled and availability state; and
3. the ability to acquire fresh provider authorization for the exact tenant/account, resource, mode, and grant.

The token returned by that final check is the token used for the write. A capability disabled after enqueue, removed authorization, or unavailable credential returns unsent work to `waiting_authorization`; a provider 401/403 on the pre-write read does the same. Once an attempt is marked sent, an uncertain outcome remains inconclusive and requires reconciliation, including a write-response 401/403. No completed or uncertain provider write is retried. Dispatch has a finite 30-minute deadline and jobs expire after seven days.

Power Platform refresh jobs are a separate read-only lifecycle. Submission records immutable principal/role/environment/type/query intent before work. A current capability decision and process-local delegated token are required before `running`; page/count progress is safe metadata, while resource rows publish atomically only after complete paging. Provider/schema/limit failure preserves the previous snapshot. Shutdown aborts in-flight reads and returns them to `waiting_authorization`; startup performs that state conversion only and never calls a provider. There is no scheduler, navigation-triggered fetch, application-token substitution or raw-response persistence.

Package inventory uses its own explicit read-only refresh jobs and principal-scoped complete observations. List/detail navigation reads PostgreSQL and does not acquire a provider token. A delegated refresh requires `CopilotPackages.Read.All`; separately enabled application refresh requires an Administrator-approved shared scope. Partial, failed, interrupted or expired scans do not replace the last complete broad observation.

Purview Audit Search is a separate on-demand provider-read lifecycle. SecurityReader is required for execution and result access; qualification approval additionally requires Administrator. Delegated jobs and every delegated record/count/export are tenant/principal-private. Application results are readable only through the current Administrator-approved shared scope and exact application qualification. The runtime accepts only code-owned presets, required operation subsets and structured filters, persists a durable operation marker before create, never retries an ambiguous POST, and requires explicit current authorization to reconcile or poll after interruption. Every physical Graph attempt reserves durable capacity immediately before dispatch; provider and local request IDs remain separate, and execution owner/version fencing prevents stale publication. Startup and routine capability refresh perform zero Graph query operations. Cancellation and deletion are local only; Microsoft may continue remote work. Stored rows are allowlisted metadata with message IDs but no prompt, response, transcript or unrestricted `auditData`. Results expire after 30 days, remain separate from local administrative audit and official usage, and associate with private Power Platform inventory only through exact Bot ID plus environment. See [the Audit Search runbook](purview-audit-search.md).

Every available package mutation requires a current server preview hash over the actor, exact native targets, frozen mutation-relevant prestate and requested intent. Jobs retain that summary and per-target prestate immutably. A tenant/package advisory lock serializes this application's local operations; under it the worker immediately rereads and hashes provider state before dispatch. Microsoft documents no ETag/`If-Match` on these endpoints, so this cannot prevent an external administrator from changing state after the reread and is never represented as provider atomicity. Block/unblock may be enabled only after directional canaries. Access replacement remains disabled even after generic qualification because its full access payload lacks an acceptable lost-update bound. Duplicate, non-UUID, unresolved, deleted or redirected principals are rejected.

Package mutation dispatch is one-shot. Bounded detail reads must observe the expected semantic state before success; HTTP `204` is only acceptance. Timeout or ambiguous state after dispatch is durable `inconclusive`. Reconciliation acquires current Operator identity and delegated package-read authority before each target and before publishing its result, honors cancellation, and performs provider reads only; it can mark an operation observed-applied, observed-not-applied/retry-eligible, or conflicting, but never automatically retries a mutation or depends on an unexpired write qualification.

Preview write qualification is separate from read evidence. An Administrator creates a 30-minute typed approval and a different Operator claims it once with current code-derived contract/configuration/delegated-auth identity. Attempted evidence has 30-day retention. The restoration service stores no token, stops before writing on intervening state, dispatches once, and qualifies only after exact semantic read-back; unknown state/criteria keys are never accepted from callers. Both directional records are required for block capability. Access and reassignment stay disabled independently of generic qualification. A changed contract/configuration/auth mode or expired record fails closed. The restoration and intervening-change stop rules are defined in [mutation-canaries.md](mutation-canaries.md).

## Audit and residual risk

Durable-operation requested, started, skipped, succeeded, failed, inconclusive and provider-verified outcomes use the existing append-only audit service with exact target, actor, operation/job/correlation identifiers and minimal before/after evidence. Capability configuration records the updating principal/revision; probe evidence retains only allowlisted diagnostic fields. Provider tokens, provider response bodies and unnecessary principal attributes are excluded from persisted diagnostics. This is ordinary local audit, not a hash chain or external checkpoint service.

Residual risks include the configured role-revalidation delay, process-local token-cache loss on restart, upstream provider/API changes, preview connector/capability-detail fields, Resource Query availability differences outside global cloud, classic/V1 bot exclusion, unpublished configuration omissions, hidden workflow environments, Azure Resource Manager Conditional Access dependencies, and the operator's responsibility to assign Entra roles correctly. No live Power Platform tenant was available for this phase, so local tests qualify bounds and failure behavior but do not claim consent, role, cloud or tenant-data success.

## Transport, admission and recovery

Production serves one HTTPS origin with HSTS for one year including subdomains, CSP limited to self (with inline CSS only), frame denial, `nosniff`, no-referrer and disabled camera/microphone/geolocation/payment/USB. Local HTTP intentionally omits HSTS. API, HTML and deep links are `no-store`; content-hashed assets are immutable for one year. API JSON is limited to 512 KiB. Provider clients use fixed HTTPS origins, manual redirect rejection, bounded pages/rows/bytes and deadlines.

One process admits at most 1,200 read or 300 write API requests per minute per trusted IP and 600 read or 200 write requests per minute per authenticated principal. Liveness, readiness and auth status are excluded. The limiter holds at most 10,000 local keys and is intentionally not a distributed quota. Uploads allow two concurrent 8 MiB/50,000-row operations. Exports have source-specific row/byte ceilings and a 15-second publication deadline. Provider workers and durable queues retain their smaller per-principal, attempt, page and concurrency bounds; durable database admission, leases and one-shot dispatch survive process restart.

The singleton database operational state is runtime-readable but operator-writable. Readiness fails for missing/changed schema, maintenance file or database maintenance mode. Safe Administrator diagnostics reveal only auth configuration, maintenance/provider admission state, schema version and fixed pool/body/export limits. Optional provider failure disables its capability rather than liveness. A logical restore migrates only a known schema prefix, verifies receipt fingerprints, invalidates sessions, staging previews, confirmations and provider qualifications, fences old ownership, marks sent writes inconclusive, and repeats bounded retention to zero before review. It compares exact current owners and authority bindings for retained caches, current official set/version deletion and selection, and Defender retained-scope revocation. Reopening repeats that comparison from one current-database snapshot while holding the restored operational row in a real transaction; unavailable or over-bound current review fails closed in maintenance. Mismatched cached content is purged, provider work remains disabled, and uncertain writes are never replayed.
