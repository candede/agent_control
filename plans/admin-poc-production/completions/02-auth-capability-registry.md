## Delivered contracts

- **Authentication:** [MSAL integration](../../../backend/src/auth/msal.ts) uses authorization code with PKCE S256, nonce, safe local return paths, native process-local MSAL cache, and identity-only initial scopes `openid profile`. [Authentication transactions](../../../backend/src/auth/flows.ts) keep state, nonce, and verifier process-local for at most ten minutes behind a random session-bound database handle; mismatch, expiry, and replay atomically consume the transaction before code redemption. Authenticated, CSRF-protected consent requests one code-owned capability group. Tenant/account metadata must agree, account switching evicts prior cache and pauses prior delegated jobs, and logout cannot race a stale role save. No token, refresh token, authorization code, state, nonce, PKCE verifier, client secret, or serialized MSAL cache is persisted.
- **Independent authorization:** Four exact, non-hierarchical roles are declared in [the Entra manifest](../../../infra/entra-app-manifest.json): `AgentControl.Reader`, `AgentControl.Operator`, `AgentControl.SecurityReader`, and `AgentControl.Administrator`. There are no bundled API grants or environment bootstrap authority. The [route-policy registry](../../../backend/src/routes/policy.ts), exhaustive source-registration test, backend middleware, repository scopes, and response shaping enforce role and data-class policy. Reader owns broad catalog/list and batch inventory; Operator keeps only exact-target reads and controls. Administrator does not inherit reader, operator, or security-reader content access; role-less recognized users can reach setup/capability diagnostics without protected tenant data or provider health. Authorized saved audit data remains readable during provider outage.
- **Capability source of truth:** [registry](../../../backend/src/services/capabilityRegistry.ts), [service](../../../backend/src/services/capabilities.ts), [repository](../../../backend/src/db/capabilities.ts), [API](../../../backend/src/routes/capabilities.ts), and shared backend/frontend types define 13 retained IDs, exact audiences/modes/grants/roles/licenses/configuration/maturity/sources, conservative status precedence, remediation, and explicit probe refresh. Evidence keys include tenant, resource principal/application, authorizing principal, capability, audience, environment, mode, permission revision, contract revision, and configuration revision. Same-key probes share one provider request; invalidation fences stale in-flight results; writes and invalidations are serialized. Evidence details are allowlisted and expired rows stop authorizing immediately while remaining diagnostic history until operator retention. Microsoft access tokens remain opaque; validated MSAL response metadata and returned delegated scopes or safely exposed app roles are authoritative, with readable JWT claims used only to reject contradictions.
- **Durability and reauthorization:** Additive migration 3 creates capability state, and additive migration 4 discards old incomplete evidence and rebuilds its key with authorizing principal and contract revision without editing migrations 1/2/3. Immediately before dispatch, delegated jobs reacquire authorization for the initiating tenant/account, recheck role/capability, and use that exact token for the write. Unsent authorization or provider 401/403 failures return the item to `waiting_authorization`; application mode is never a delegated fallback, and already-sent uncertain work is not replayed.
- **Trust boundary:** [security model](../../../docs/security-model.md) documents single-origin authorization, data classes, bounded role revalidation, external-revocation delay, session/token handling, CSRF, safe redirects, provider URL/next-link checks, and durable work. Provider targets are HTTPS allowlisted origins/paths before bearer attachment; cross-origin redirects are rejected. `FRONTEND_ORIGIN` is the sole canonical origin and `REDIRECT_URI` must match it exactly at `/api/auth/callback`, including the same port. Incomplete auth configuration fails, App Service identity derives the trusted proxy boundary, and session secrets require at least 32 bytes. These settings directly replace Phase 01's `APP_ORIGIN`; Compose and runtime harnesses were updated together, with no alias or dual-origin behavior.
- **Setup contract:** [deployment guide](../../../docs/deployment-setup.md) and [dated provider inventory](../../../docs/provider-contract-inventory-2026-09-08.md) record local reply URL, four-role import, incremental consent, exact source links, and the six existing-vault names. Runtime receives only tenant/client/client-secret/session/app-database values; `agent-control-postgres-admin-password` remains operator-only and differs from the app password. Phase 12 owns `deploy-azure.ps1`; the legacy `deploy-production.ps1` was neither modified nor run.
- **Frontend contract:** [authorization matrix](../../../frontend/src/authorization.ts), [application shell](../../../frontend/src/App.tsx), API types/client, package table, bulk controls, and reporting view separate role navigation, loading, controls, and data. Reader receives broad package inventory without exact assignments; Operator does not auto-load or refresh that catalog and uses exact-target backend contracts for controls; SecurityReader receives local audit; Administrator receives setup/configuration and official aggregate report administration without implicit access to the other content classes.
- **Continuity:** Browser report storage remains `agent-control:usage-reports:v1` and no old-origin storage was read, migrated, or deleted. No Azure/Entra/provider write was attempted. The retained volume and restricted secrets were reused, schema `[1,2,3,4]` was observed, and the persistence harness proved nonempty fixture fingerprints and exact secret/settings continuity across stop/start and redeploy.
