# Agent Control

Agent Control helps administrators understand and manage their organization's AI agents in one place: discover agents, understand adoption and user-agent relationships, investigate activity, and take supported access-control actions. It uses Express, React, Microsoft Graph and the Power Platform Resource Query API. One Node process serves the API and built UI; PostgreSQL owns sessions, on-demand jobs, private inventory snapshots, minimized Purview audit-search results, official Microsoft 365 usage reports and append-only administrative audit.

The binding [13-phase plan](plans/admin-poc-production/README.md) distinguishes delivered work from planned integrations. Phases 01-03 provide the local runtime, persistence, identity/capability contracts, Permissions and shared gates. Phase 04 adds explicit delegated Power Platform inventory refreshes, private normalized snapshots, exact typed identity association and the Inventory Explorer. Phase 05 adds saved package observations, explicit refresh jobs, confirmed/fenced package mutations, provider readback, read-only reconciliation and an optional principal-separated durable canary restoration command. Phase 06 adds backend-owned ingestion of the three official Microsoft 365 admin-center usage exports. Phase 07 adds bounded, on-demand Microsoft Purview Audit Search with private minimized results and a separate local/Purview audit view. Phase 08 adds bounded Defender hunting. Phase 09 adds direct Copilot Studio quarantine status plus exact, confirmed, durable quarantine/restoration controls in Inventory Explorer. The unified workbench now uses canonical `/agents`, `/power-platform`, `/users`, `/sync`, `/audit`, `/security`, `/permissions` and `/jobs` routes served by the same Express artifact; retired `/official-usage` bookmarks migrate to report workflows in Sync. No live package or quarantine canary, quarantine status read, Purview lifecycle or Defender query was authorized during those phases in the unconfigured local environment; this is missing live evidence, not a prerequisite for ordinary operations. Implemented package access, block/unblock and quarantine changes run on demand for an authorized, confirming Admin. Owner reassignment has no implemented product workflow or documented owner readback. No transcripts, continuous collection or raw archives are implemented.

## Unified Workbench

The eight canonical views use two hierarchical roles. `AgentControl.Viewer` can observe every view, including exact targets and assignments, user-level accepted reports, security results, and local administrative audit; it can run and cancel its own delegated read, refresh, search, and export lifecycle. Explicit delegated Purview/Defender requests establish their own principal evidence without a separate qualification ritual. `AgentControl.Admin` includes all Viewer access and adds supported changes, imports, configuration, mutation and application/shared-scope approvals, and mutation-job controls.

- Agents represents each resolved logical agent once in a tenant/account-private canonical registry, not once per API result. Several catalog packages can belong to one native agent without losing their separate access/block targets; the same row also retains Power Platform configuration and eligible quarantine controls. Reconciliation serializes with source publication and runs before filtering, counts, or pagination. Publication carries existing source memberships forward without inheriting old matching proof, so retention before the next read does not discard unchanged canonical identities. Canonical `agent:<uuid>` links remain stable across ordinary refreshes; exact package and environment/native links resolve to the containing row. Power Platform retains non-agent resources, including apps, flows, connectors and environments.
- The Agents page starts with four source-qualified counts: **Agents in repository**, **Available to end users**, distinct reported-used agents across retained imports, and agents reported active in the last 30 UTC calendar days. Repository membership includes agents that users cannot access; end-user availability requires an unblocked package available to all or some users and no known native quarantine, across hosts (not just Teams). Creation, installation, publication and past use alone do not qualify. The first two cards clear table filters and show their matching lists. Inventory counts cover the complete authorized saved repository and Power Platform data before filtering/paging, with partial coverage noted inside the cards. Report counts include identities absent from saved inventory and must not be added to inventory totals. The overview has no explanatory footer or embedded report explorer; selected-report dates share the table's existing Columns toolbar when usage columns are shown. Agent details use four strictly agent-scoped tabs: **Overview**, **Usage & users**, **Manage**, and **Activity**. Existing `package` and `power-platform` detail bookmarks both open Overview; the latter also expands technical details.
- Overview combines the agent's full sanitized description, publisher/version, status, availability, installation, native ownership/configuration and connected-service metadata, regardless of their source. Opening Overview or Manage reads authorized saved package details automatically, without refreshing the package or requiring a nested details panel. Sparse agents retain their available metadata and explicit missing-data states. Multiple published versions have an exact detail selector, while aggregate status/access labels remain clearly scoped to all versions. A missing or invalid selected version fails closed rather than silently selecting another management target. Reported connector/operation totals remain separate from bounded saved details and detected metadata references; neither is presented as a live-connection count. Explicit zero stays zero, unknown stays unknown, and long reference lists are paged without truncating their totals.
- Manage embeds the **Available to / Installed for** editor directly: scope choices, directory picker, assignments and Apply are part of the agent modal, not launcher buttons or another editing screen. Block/Unblock sits beside the exact selected version; eligible quarantine remains a separate control. Directory names are resolved only for the active setting when permitted, while Viewers can read saved assignment IDs without directory or write access. Apply refreshes the exact package before requesting its server-issued preview; access and block confirmations appear inside the same agent modal. Cancelling confirmation preserves the draft, settings have independent drafts, and changing versions cannot carry a draft to another target. Successful access changes reload saved settings. The standalone and bulk editors reuse the same form. Source IDs, link evidence and raw diagnostics remain under technical details.
- **Agents** owns current agent usage, while exact source-snapshot tenant totals and report-only agent comparisons remain in the read-only **Sync > Manage reports** snapshot inspector; reported-user breakdowns are available in **Users**. Agents automatically matches a reported Agent ID to the exact full, case-sensitive Graph package ID in the viewer's authorized current saved inventory, then uses its existing canonical membership, including any established Power Platform link. Names, GUID fragments, manifest IDs and Entra application IDs are not alternative report keys. The table, **Usage & users**, sorting, filtering and export share this read-time projection; no manual setup, provider calls or association writes are needed. Opening an agent modal never fetches tenant report candidates or renders tenant totals. Missing matches remain unavailable, not zero. Existing explicit reviewed associations remain labelled report-set-scoped overrides; automatic matches are labelled exact package-ID matches, not administrator reviews. Reported-user links retain the exact report identity and set. Stale reports, inferred activity ranges, missing data, and source-total disagreements remain visible. Usage attribution never grants management permissions or creates native identity links.
- Users offers **M365 Copilot licenses** and **Reported activity**. The license view defaults to effectively **Licensed users**, including people without matched usage. **Active M365 Copilot licensed users** and the adoption cards require verified active paid features, not just a containing product assignment, basic Copilot Chat access or recent usage. **All checked users** retains the broader directory discovery cohort for diagnostics; an E7 user with all paid Copilot features disabled shows **No active M365 Copilot license**, not a positive licensed label. Basic Chat may still be available without the paid license or when paid features are not enabled; its access and usage are not measured here. Reported activity owns the user-report filters, rankings, and CSV export formerly on Official usage. Its paginated user list includes concealed and unlinked report identities; explicit, searchable, paginated per-user agent details replace the unscalable agent-column matrix. An explicit `0` differs from missing evidence. Current paid-license context requires an existing unique directory/report link for the exact report set and versions plus effective paid-feature evidence; unresolved or historical identities remain **License not verified**, not inferred to be basic or unlicensed. Exact agent filters and retained snapshots are preserved without guessing identity.
- **Sync > Import reports** and **Sync > Manage reports** replace the standalone Official usage page. Manage reports owns one paginated retained-history table, with Admin actions and read-only Viewer viewing, plus import lineage and deduplication accounting. Its deduplicated cross-import agent locator preserves exact report identities absent from newer imports or saved inventory; it does not repeat the cumulative summary cards on Agents. Optional UTC date filters select observed agent last-activity evidence, not reconstructed daily response totals. The snapshot inspector retains unique source evidence, exact tenant response/user measures, raw report-only rows, comparisons, and agent CSV exports for one exact bundle; overlapping rolling-window totals are never added. Current agent usage belongs to Agents, licensing and user activity to Users, and collection/import/report management to Sync.
- Adoption insights retain contextual links to the exact reported agent and source snapshot inside Sync, rather than generic Users or retired-page shortcuts. Missing-report guidance points to the existing primary navigation.
- An agent's Activity tab contains only its saved associated audit and security observations, with links to those records' investigations. Missing associations do not imply zero usage or assert that an agent is safe. Tenant-wide investigation and management audit remain in the Audit and Security workbench views, not in the agent modal. Opening these views never starts a provider query. Inapplicable quarantine controls are not promoted for package-only agents; all eligible controls retain exact-target confirmation and authorization checks.
- Sync (`/sync`) groups data collection, source coverage diagnostics, exact matching-detail refreshes, Power Platform agent refresh/export, and retained sync history. Agents keeps a compact count and partial-coverage indicator; package and quarantine bulk controls appear only for a selection or retained work. Select packages on Agents before opening Sync to refresh their matching details; tab navigation preserves the selection and filters.
- Agents keeps its basic controls to two rows on desktop/tablet: Search, **Show agents**, Built with, Available to, Host, Created within, Package status, sorting, **Advanced filters**, and Clear filters. Advanced contains Publisher and an environment dropdown with a separate partial-name/ID search; searching narrows the choices, and selecting applies the filter. Choices come from the complete authorized saved agent inventory, not the current page, using saved environment names when available and explicit unnamed-ID labels otherwise. Hidden advanced values stay applied with an active count; bookmarked/history-restored advanced values expand automatically. Source and link-state filters are removed, including obsolete URL restrictions, while exact agent and job links remain valid. Built with and creation age include saved Copilot Studio agent properties, regardless of package presence; package status, publisher, availability, and host still require matching saved package properties and do not infer missing values. Clear filters resets filter values without changing sorting. Export sits beside the Agents heading.
- Built with filtering uses the same canonical authoring labels as its choices, including provider spellings displayed as Copilot Studio. Modified sorting compares actual instants across saved package modification and Power Platform publication/creation times, using the latest instant in each grouped row before pagination. Equal instants use the exact row ID as a tie-breaker; undated rows remain first for oldest-first and last for newest-first sorting.
- Identity matching distinguishes Studio environment/CDS/schema identities, declarative manifest identities, and custom-engine bot application identities. Declarative packages link only when their manifest ID agrees with both the native ID and GUID schema name of one authorized agent resource. Custom-engine package representations can share one row when their declared bot application identities agree and the native association is unique. Equal names, package-management app IDs, or blueprint IDs are never merge evidence. Source-specific Graph and Power Platform agent identity IDs can differ even when the exact native agent agrees; this difference is retained as a diagnostic, not a false native-identity conflict. Ambiguous native/environment claims stay separate.
- Source details show exact identifier kinds, observation times and authorized related observations. Links distinguish corroborated source metadata from a documented Microsoft identity guarantee. A manifest, bot application ID, name, package ID, blueprint, or Defender ID never becomes a CDS quarantine target. An alias package cannot refresh another package's expired native-control proof. Official usage is authoritative only from the three companion Microsoft exports.
- Jobs shows minimized, authorized user-work status and explicit recovery. Navigation loads saved data only. Progress polling is sequential and finite; waiting-for-authorization work requires an explicit action. Uncertain writes offer GET-only reconciliation, never replay or automatic inverse operations.
- Package access labels, mutation preparation and provider readback share status normalization, including the existing `deployedToNoOne` and `deployedToNone` compatibility spellings. The combined **Allowed for Some or All** inventory facet and filter use the same aliases, ignoring case and separators in both saved-package SQL and unified inventory filtering. Raw provider status strings, including future values, remain unchanged in responses and exact-value filters. Explicit scopes take precedence over principal entries; missing or unknown status still uses the existing principal-based fallback and remains unknown when no principals are present. Package inventory rejects malformed collection pages and continuation links rather than treating them as a complete snapshot.
- Downloads are authenticated server exports tied to an exact saved selection. Agents exports one row per logical agent, retaining every associated package and the observed native configuration. Each package-state entry retains its exact ID and version; a missing version remains `null`. With no selection it exports all filtered pages, including organization/usage and environment filters; exact canonical/package/native selections are resolved and deduplicated on the server. Column visibility does not remove approved CSV fields. A scoped saved-source and usage revision fences refreshes, exact overlays, environment changes, report selection/deletion, reporting associations, expiry and cleanup; audit-reference filters are separately revalidated. Inventory exports are capped at 5,000 rows, official exports at 100,000 output rows, Defender at 200 rows, and local administrative audit at 100 exact selected events. CSV generation is bounded to 8 MB (2 MB for Defender; 1 MB for local administrative audit), with a 15-second publication deadline and disconnect handling. Oversize selections fail rather than silently truncate. Current session, role and source validity are checked again before publication; stale scope, deletion or revocation stops the download.
- CSV formulas are neutralized and only approved fields leave the server. Audit records source/selection/count metadata, never exported rows. No export file, bearer link, original CSV archive, transcript viewer or maintenance console is created.

The local workbench can show truthful setup/disabled states without live provider credentials. Deterministic browser fixtures are isolated test tooling, not qualification or a production sign-in bypass. See the [Phase 10 completion](plans/admin-poc-production/completions/10-unified-admin-workbench.md) for exact tested commands and retained-environment evidence.

## First-use data sync

Data sync coordinates saved Microsoft 365 Copilot entitlement evidence and app-activity data, Graph packages, and Power Platform resources. The Users count is **directory users checked**, not effectively licensed users or tenant headcount. Graph filters the whole tenant for products containing paid Copilot features and returns per-user feature evidence in pages, so the app does not need one license request per user. A 30,000-account tenant may legitimately have only about 4,000 matching candidates and fewer effectively licensed users, because bundled Copilot features can be disabled. Official usage CSVs have a separate import workflow. First use is based on persisted synchronization state, not an empty table: an authorized scan that finds zero objects is different from a source that was never queried, failed, or requires permission.

Users derives effective paid **Microsoft 365 Copilot licensing** from verified active paid features, not the state of a containing product or SKU. Standalone and bundled Copilot follow the same service-plan rules; an assigned product with no active paid features qualifies for neither a positive licensed label nor paid-license adoption counts. Paid-feature labels distinguish active, grace period, not enabled, suspended, locked out, unverified and partially active. None means that basic Copilot Chat is disabled. Directory paging allows 1,000 pages with the existing 100,000-observed-row bound and requires every matching page to reconcile with Graph's counts; incomplete collections are never saved as complete. Migration 37 deletes the app's old cached Users-sync data and resets its saved counts once; run Users sync after applying that migration. The effective-entitlement correction and paging fix add no migration or reset of current-format snapshots. See [Paid Copilot license detection and usage](docs/copilot-license-usage.md).

For official usage, an Admin exports the **Agents**, **Users & agents**, and **Users** CSVs from Microsoft 365 admin center **Reports > Usage > Microsoft Copilot > Agents** using the same 7- or 30-day selection. **Sync > Import reports** opens a dedicated modal wizard: **Files > Validation > Review & accept > Result**. Report management and legacy-browser cleanup are separate from this approval flow. Reports remain unavailable until a complete validated bundle is accepted, but do not block automatic inventory/user sync. Viewers can synchronize their own authorized read sources; acceptance still requires Admin. Existing accepted reports are preserved during a full resync.

Open the **Sync** tab to use the dedicated data-sync page. First use adds a **Setup needed** hint for automatic sources without opening a modal, redirecting other pages, or starting provider reads. **Workspace data** always shows all three automatic sources and their last successful counts/times, independent of the latest or selected run. A users-only sync does not replace Graph or Power Platform state; a failed attempt does not turn its observed count into a saved total. The separate CSV section reflects the currently accepted report bundle, even after a limited sync or report selection/deletion.

Active collection has a prominent progress panel with queued/running/blocked source states, real per-stage observed counts, source messages, and update times. Its bar measures completed automatic sources, not elapsed time or a guessed total-object percentage. Counts are not added across different source types and can restart when collection enters a new stage. Completed runs have a compact, explicitly scoped result, while overall workspace counts stay visible. **Check status** only reloads status; it never starts collection. **Resume updates** appears when the polling budget is exhausted.

**Sync history** is a table of recent retained runs, ordered by original start time, with scope, outcome, completion counts, and duration where recorded. Filters and paging apply to the bounded recent records, not a complete audit archive. **View details** opens exact run messages, identifiers, and recovery controls in a separate dialog without substituting historical results for workspace state. **Source jobs** preserves older standalone and underlying provider-job links; CSV snapshot history is in **Sync > Manage reports**. Jobs remains the cross-workbench job view. Old `/agents?syncRun=...` bookmarks redirect to `/sync?syncRun=...`.

**Inventory health > View diagnostics** contains automatic saved-inventory checks, identity-matching evidence, and source-specific repair/export tools. It is not an additional approval step. Routine collection and CSV import do not require expanding diagnostic sections.

The three collection actions are:

- **Start initial sync** collects users and inventory for first-use setup without deleting saved data.
- **Sync all sources** reads the latest users and inventory, keeping previous successful snapshots until replacements are ready. Each source row also has a scoped **Sync** action.
- **Reset saved data...** opens a separate confirmation requiring acknowledgement, then clears only the current tenant/account's saved users, license/app-activity snapshots, Graph packages, Power Platform inventory, and their synchronization success markers before a full read. These views can be empty until collection succeeds; failure or cancellation does not restore cleared data. Accepted usage reports, report history, audit records, configuration, jobs, and other accounts' saved data are preserved. It is not a database reset and does not change Microsoft settings.

Provider reads run in durable source jobs. Switching tabs does not cancel or restart them; return to **Sync** to check progress. Retry resumes incomplete sources without replaying successful collection, and restart or sign-out requires renewed authorization before more provider work. Cancellation, sign-out, and shutdown join pending admission and source work before reporting completion; overlapping retries of the same run are rejected. An expired retained child job does not prevent cancellation or an explicit retry of its incomplete source. New default initial, incremental, and full runs include only the three automatic sources. Explicit `usage_reports` requests and retained older runs with manual steps remain supported; finish their import or cancel the waiting run before starting another run. API full-resync requests remain nondestructive unless they explicitly opt into `clearSavedData: true`.

Retry controls wait for running collection to settle and remain disabled while a different run is running or waiting. Incomplete sources on the same waiting run can still be retried.

Status polling has a five-minute budget per activation or explicit refresh; superseded requests cannot pause a newer polling cycle. Browsing retained runs does not stop current source completions from refreshing saved views, and status reloads preserve change detection for the selected run. Changing the selected run during an action still checks saved status afterward, including when the action response is lost, without replaying the action or replacing the selected historical run.

The current run follows the most recently updated run, including retries of older runs; retained history stays ordered by original start time. Overall source state comes from persisted success markers, not that run's scope or progress. When a saved-status read reports cleared sources, saved-view invalidation also covers failed attempts that retained snapshots and sources omitted by a prior limited run, including recovery after a lost clean-resync response.

Existing installations must apply all pending migrations through version 38 and reapply runtime grants through the normal operator deployment workflow before starting this runtime. Migration 32 adds canonical entities and unique, scoped source memberships while preserving existing source snapshots, audit, reports, jobs, and sessions; migration 33 adds inventory queried-type metadata, migration 34 adds reviewed usage associations, and migration 35 adds saved agent-people data. Migration 36 permits clean full resyncs of the three automatic sources while retaining valid legacy four-source runs; it does not change the cleanup scope or add progress tables. Migration 37 clears cached directory/license and Copilot app-activity snapshots, their source state, and Users success markers across this app database once; other inventory, imported reports, sessions and agent-people caches are unchanged. A fresh Users sync is required; Microsoft users and license assignments are never deleted. Migration 38 permits both verified stages of a package access canary to retain qualification evidence for the same action; it does not alter block/unblock uniqueness or runtime grants. Verify readiness as `agentcontrol_app`, not the operator: associations permit `SELECT`, `INSERT` and `DELETE`, while association revision state is read-only to the runtime. Clean resync clears that account's canonical inventory together with its source snapshots, and rejects unfinished standalone package or Power Platform refresh jobs without deleting data; finish or cancel those jobs first.

Package identity metadata is parsed and its native fields are validated before storage, so a large authoring definition cannot cut off its native IDs. Complete package element definitions are retained within the provider/storage byte budgets, preserving the Connected services view rather than slicing JSON or discarding configuration. Malformed or oversized observations fail explicitly. A saved snapshot from an older runtime can contain already-truncated metadata. Sync reports invalid matching details separately from identities checked; refresh the affected packages or run a confirmed clean resync to replace those observations. Rebuilding the canonical registry does not require resetting the database or removing accepted reports.

Saved user/license and app-activity reads remain tenant/principal-private. Current accepted agent-usage reports are joined when those saved users are read, so a new report import does not require another Graph scan. Audit Search and Defender remain separate, bounded, explicitly requested investigations; onboarding does not claim to collect unlimited logs or transcripts. Management actions continue to revalidate live authorization and exact target state independently of saved inventory.

## Local Deployment

Host prerequisites: PowerShell 7, company-approved Docker Engine/Desktop with Compose v2 or newer, and a browser. Node, npm, Vite, PostgreSQL, tests and browser automation run **inside Docker**. Initial onboarding also requires an approved single-tenant Entra application's tenant ID, client ID and client secret. No Azure subscription or Key Vault is required for local deployment.

Local deployment does **not** load a repository `.env` file. [deploy-local.ps1](deploy-local.ps1) accepts the commands `start` (the default), `stop`, and `edit-config`, positionally or via `-Command` / `-Action`, plus `-Project` (default `agent-control`). After software preflight, first start or missing settings trigger a wizard for the tenant ID, client ID, hidden client secret and local port (default `3001`). Configuration is saved in the fixed repository-root `.local/<lowercase-project>/` directory; custom state locations are not supported. Configured starts reuse saved settings, including the port and optional public URL, without prompting. The script regenerates `compose.env` for Docker Compose; do not edit that generated file.

From the repository root:

```powershell
pwsh ./deploy-local.ps1 start
# Omitting start is equivalent:
pwsh ./deploy-local.ps1
```

Open **http://localhost:3001**, or `http://localhost:<saved-port>` when configured differently, unless a public URL is saved; in that case open the public URL. Use this single canonical origin, not a second `127.0.0.1` browser origin. Every `start` first builds the operator and qualifies the software in a uniquely named, disposable Compose project. Its PostgreSQL uses memory-only fixture data, synthetic passwords, no application secrets and no external network. Backend/frontend tests, backend typecheck, frontend lint and the production build must pass, and fixture cleanup must succeed, before the runtime image is built or deployment enters maintenance. Only then does deployment stop/drain the app, start the retained PostgreSQL service, apply serialized forward migrations and start the app, waiting up to 90 seconds for readiness. A software/build failure leaves the existing app, database and maintenance state unchanged. Failure returns nonzero without resetting data or announcing deployment success. Two long-running services remain: `app` and `postgres`.

The final summary reports the automated check results and local app readiness.

- Default project: `agent-control`; volume: `agent-control_data`; network: `agent-control_default`.
- The app listens on all interfaces **inside** its container but publishes only on loopback at the saved host port (default `127.0.0.1:3001`). PostgreSQL has no published host port. The project bridge permits normal outbound DNS/HTTPS for Entra/Graph.
- Use `-Project <name>` for a separate installation and select an available host port from `1024` through `65535` in the wizard. Project names are 3-40 letters, digits or hyphens, starting with a letter, and are normalized to lowercase: `-Project newCustomer` uses `.local/newcustomer/` and Docker project `newcustomer`. Keep the same project on reruns; its port is saved automatically. Repository paths with spaces are supported; newlines and single quotes are rejected.
- Normal redeployment preserves the volume and secrets. Before migrations it closes admissions and stops/drains the app, with a 130-second grace period. It never imports legacy data or resets storage automatically.
- `GET /api/health` returns only liveness; `/api/ready` validates database and migration checksums; `/api/auth/status` describes setup. Diagnostics require authentication. Unknown API routes and missing assets return errors, not SPA HTML.

### Sign-In Setup

Use an existing approved single-tenant Entra web application. Its default local Web reply URL is exactly `http://localhost:3001/api/auth/callback`. A different wizard port requires the matching registered Web reply URL `http://localhost:<saved-port>/api/auth/callback`. The script does not modify app registrations or grants.

```powershell
pwsh ./deploy-local.ps1 start -Project newCustomer
# The default command also supports a project:
pwsh ./deploy-local.ps1 -Project newCustomer
```

For a new project, the wizard asks for the tenant GUID, client/application GUID, client secret **value** (not the secret ID), and port (Enter accepts `3001`). Secret input is hidden and stored only in the project's restricted `secrets/client-secret` file; IDs and port are saved in `settings.json`. Existing projects are prompted only for missing settings or an absent/empty secret. Existing values and database/session secrets are preserved. Use a separate project for another tenant.

Before asking for settings, onboarding and `edit-config` display the registered-app permission checklist: Graph and Power Platform delegated permissions, optional app-only permissions, administrator consent, app-role assignments and provider prerequisites. Sign-in requests all implemented delegated permissions; app-only permissions remain separately configured. The wizard neither grants permissions nor verifies live consent. Configured starts do not repeat this guidance.

Run the same command next time to reuse the saved configuration. Identity and port command-line arguments are not accepted. Initial or incomplete onboarding requires an interactive terminal; required identity values cannot be blank, and malformed GUIDs or invalid ports are prompted again. Complete onboarding interactively before unattended `start` runs. `stop` and operator-only maintenance helpers do not prompt for identity. The wizard validates input format, not live Entra credentials, permissions or consent. No fake identity or runtime auth bypass exists.

To review or change saved configuration:

```powershell
pwsh ./deploy-local.ps1 edit-config -Project newCustomer
```

`edit-config` prompts for tenant ID, client ID, hidden client secret, local port and public URL. Enter preserves each current value, including leaving an unconfigured identity field unset; the current secret is never displayed. To change only the port, press Enter at the three identity prompts, enter the new port, and press Enter at the public URL prompt. `start` still asks for any missing identity values before launching. If nothing changes, settings are not rewritten and a running app is left running. Accepted changes to the client ID, client secret, port or public URL stop the app safely and leave it stopped; run `start` explicitly afterward. Update the Entra Web reply URL before restarting if the canonical origin changes.

#### Testing through a dev tunnel

```powershell
pwsh ./deploy-local.ps1 -Action edit-config -Project newCustomer
# Keep the identity fields and local port, then enter the HTTPS public URL:
# https://your-tunnel.devtunnels.ms
pwsh ./deploy-local.ps1 start -Project newCustomer
```

Before starting, add `https://your-tunnel.devtunnels.ms/api/auth/callback` as a **Web** redirect URI in your Entra app registration. Start sign-in from the HTTPS tunnel URL, not localhost. The public URL must be a canonical HTTPS origin without a trailing slash, path, query or fragment. Do not append the local port: the tunnel forwards to the saved local port (for example `3002`) independently.

Persist header preservation on the existing tunnel port, then host the tunnel in a separate terminal. Replace `YOUR_TUNNEL_ID` and `3002` with your existing tunnel ID and saved local port, retaining your approved tunnel access controls:

```powershell
devtunnel port update YOUR_TUNNEL_ID -p 3002 --host-header unchanged --origin-header unchanged
devtunnel host YOUR_TUNNEL_ID --host-header unchanged --origin-header unchanged
```

Dev Tunnel rewrites `Origin` to localhost by default. Host flags alone may leave an existing port's rewrite behavior unchanged, especially when hosting its saved ports without `-p`; use `devtunnel port update` explicitly. Sign-in and page reads can work while permission checks and sign-out fail with `A same-origin request is required`. This is not an Entra permission failure. Saving the app's public URL does not configure the tunnel port. Never replace the header with a fixed trusted origin or disable same-origin checks: preserve the browser's actual origin so cross-origin requests remain rejected. The port update can take effect while the tunnel is running; reload its public URL and retry **Check status** or **Sign out**. Origin rejection responses include `details.expectedOrigin` and `details.receivedOrigin` for diagnosing any remaining mismatch without exposing cookies or tokens.

The optional `publicUrl` project setting determines `FRONTEND_ORIGIN` and the same-origin `REDIRECT_URI`. It also enables `TRUST_PROXY=1` for one controlled tunnel/reverse-proxy hop; that proxy must forward `X-Forwarded-Proto: https` for secure session cookies. The app remains published only on loopback. Local readiness checks do not depend on the tunnel, and successful deployment does not verify tunnel reachability or the Entra registration.

Press Enter to retain the public URL. Enter `local` to reset it to automatic `http://localhost:<saved-port>` and disable proxy trust. Existing projects without this setting keep localhost behavior and do not receive a new prompt on `start`. A saved public URL stays unchanged when the local port changes. If the tunnel hostname changes, rerun `edit-config` and update the registered callback. No manual Compose edits are needed.

The tenant ID can change before the project has a database volume, and a previously missing tenant ID can be filled in. Once a volume exists, changing a nonempty saved tenant ID is rejected before stopping the app or writing settings. Configuration edits never migrate existing data between tenants; use a separate project for another tenant.

Changing the saved client/application ID on an existing volume stops the app and records `control/reauthenticate`. The next `start` clears only persisted login sessions before reopening the app, requiring sign-in under the new app registration. The session-signing secret and all business data remain untouched. Secret-only and port-only edits do not schedule a session purge.

Normal sign-in requests outstanding consent for all implemented delegated capabilities up front: Graph directory, package catalog and changes (`CopilotPackages.ReadWrite.All`), Purview and Defender, plus Power Platform inventory and quarantine. MSAL `extraScopesToConsent` includes additional scopes at authorization time; each later token request remains account-, resource- and capability-specific. Already approved permissions normally do not trigger another consent screen. Application permissions are not requested; supported write operations still require the internal Admin role and exact-target confirmation. Authenticated, CSRF-protected capability recovery remains available and does not force another consent screen when Entra needs only sign-in. Existing installations can use normal sign-in again after redeployment to request newly included scopes. Consent does not run investigations, make provider changes, assign app/service roles, or provide licenses. Do not add broad grants to conceal an unavailable or unproven provider contract.

Import only the `appRoles` from [infra/entra-app-manifest.json](infra/entra-app-manifest.json) into the approved single-tenant app registration while preserving its other configuration. It defines exactly `AgentControl.Viewer` and `AgentControl.Admin`, with Admin including Viewer access. Set **Assignment required?** to **Yes** and assign Viewer or Admin through the Enterprise application; one assignment is sufficient and recommended, while overlapping current direct/group assignments simply evaluate to the Admin superset. A recognized unassigned or legacy-role-only user receives setup diagnostics and no protected data; no role is inferred or auto-promoted. [docs/security-model.md](docs/security-model.md) defines the role/data matrix and [docs/deployment-setup.md](docs/deployment-setup.md) defines setup and safe role migration.

Authenticated assigned users can read the side-effect-free `GET /api/capabilities`, which returns `{ value: CapabilityView[] }`. After the catalog loads, the UI sends one CSRF-protected `POST /api/capabilities/check` with no body or an empty object and receives the same shape. Nonempty, array, or `null` bodies fail with `400 invalid_request`: **Automatic capability checks do not accept request parameters.** Viewer is sufficient and Admin inherits that access; the frontend does not call the check route for an unassigned or legacy-role-only account. The backend does not independently schedule page-load work. Bounded delegated checks refresh session evidence when the frontend calls after authentication/consent and active expiry; ordinary delegated operations also perform one safe read-through refresh when eligible evidence is absent or expired. Only Admin can change capability configuration. Viewer can observe broad inventory and exact targets and submit ordinary bounded delegated reads, but cannot submit provider changes, imports, configuration, mutation or application/shared-scope approvals, or mutation-job controls. Unknown or checking evidence is not failure, and missing credentials never produce synthetic provider results. Microsoft access tokens are treated as opaque: MSAL response metadata and returned scopes/roles are authoritative, while readable JWT claims are used only to reject contradictions. ```powershell

pwsh ./deploy-local.ps1 start
pwsh ./deploy-local.ps1 edit-config

The receipt records SHA-256, schema and per-table counts/content fingerprints, not row contents. Its `-BackupFile` parameter selects an explicit new filename in an existing restricted directory. Existing files are never overwritten.

Restore always creates a **new isolated database**, never the source/default database. Follow the [operator restore and reopen procedure](docs/operations.md#backup-and-isolated-restore), selecting the exact project and an isolated target such as `agentcontrol_restore_check`.

`pg_restore` runs transactionally, followed by schema/count/content validation and explicit grants. Existing targets and changed receipts fail. A failed restore target remains isolated for review; the source is unchanged. Review retained data and run operator retention before any separately approved promotion. Phase 01 does not switch the running app to a restored database. After a successful check, remove only that exact isolated target:

All available single, selected bulk and block-all mutation routes require a current server-issued preview with `risk: true`, a confirmation hash, and a durable `Idempotency-Key`, then return **202 durable jobs**. The preview includes operation, exact targets and current/requested state, Microsoft Graph endpoint/maturity, delegated permission, actor, affected principal count and rollback limits. Same-key/same-confirmation retries return the original job even after saved package state changes; another payload returns 409. Access and block/unblock operations need no prior canary or additional configuration. Reassignment has no implemented product workflow. Job states are `queued`, `running`, `waiting_authorization`, `succeeded`, `failed`, `cancelled` and `partial`, with no `completed` alias. Items also distinguish `skipped` and `inconclusive`.

- At most two in-process workers, five unfinished jobs per principal and 5,000 items per job. No recurring provider refresh or startup collection.
- Database-time leases last 120 seconds with owner/version fences; up to ten claims, a 30-minute dispatch deadline and seven-day retention. Stale workers cannot commit outcomes or dispatch another item.
- Intent/attempt audit is persisted before remote dispatch. A per-tenant/package advisory lock serializes local operations; under that lock the worker rereads the exact target and compares the frozen mutation-state hash. It then rechecks role/capability and reacquires the exact delegated tenant/account/resource authorization. Writes dispatch once and are never automatically retried. Successful outcomes require bounded provider readback; uncertain accepted writes remain `inconclusive`. `POST /api/agents/bulk-jobs/:id/reconcile` requires current `AgentControl.Admin` plus delegated `CopilotPackages.Read.All`, revalidates around each result, honors cancellation, performs provider reads only and never requires a still-qualified write capability.
- Package mutation-state hashes use fixed field order and canonical principal identities/order, independent of JSONB object-key ordering. Existing captured-state hashes remain unchanged, so read-only reconciliation compares stored and observed access state without treating serialization order as an external change.
- Verified changes, verified no-op outcomes, and authorized reconciliation store the already-obtained exact package readback in the same transaction as the fenced job outcome and audit receipt. This advances the saved inventory revision without another provider request or a fabricated refresh job. The UI reloads saved inventory so membership, counts, sorting and exports reflect that observation. An intervening confirmed clear/resync fences an older in-flight observation; explicit read-only reconciliation can obtain and publish a fresh observation afterward.
- Restart cannot recover MSAL tokens. Unsent delegated work waits for current authentication and explicit resume; completed/uncertain items never replay. Cancel stops unsent items, not an already accepted remote operation.
- Poll `GET /api/agents/bulk-jobs/:id`; cancel with `POST .../:id/cancel`; resume unsent work with `POST .../:id/resume` and `{ "confirmed": true }`; reconcile inconclusive items with `POST .../:id/reconcile`. Tenant/principal filtering applies before job, session and audit access.
- Sessions expire after eight hours, IDs regenerate at login, and only allowlisted account/user state plus a random authentication-transaction handle is serialized. OAuth state, nonce, PKCE verifier, tokens, and MSAL cache blobs never enter PostgreSQL. One-time process-local authentication transactions expire after ten minutes.
- Administrative audit appends confirmed request, attempt start and outcome/reconciliation rows and reads a projection. Unknown legacy tenant attribution is not exposed by scoped app routes.

Requests cap JSON at 512 KiB; package pages cap at 100/5,000 total rows and 2 MB per response; package readiness, inventory-page and detail reads each have a thirty-second provider budget. Other provider requests, including package mutations, retain ten-second limits. Readiness separately bounds token acquisition to ten seconds. Successful package response bodies share the read deadline, and inventory jobs retain their overall execution deadline. Ordinary read retries cap at three with fallback delays capped at 30 seconds; confirmed inventory throttling allows six attempts with 30/60/120-second backoff. Valid provider `Retry-After` values up to five minutes are honored without shortening them; longer cooldowns fail the read rather than retry early. Mutations never retry. Directory search returns at most 50 principals, resolves at most 500 native Entra UUIDs with concurrency eight, rejects duplicate/deleted/unresolved identities and rejects a Graph response whose ID differs from the exact requested ID. Unknown package fields are omitted with value-free schema diagnostics. Package responses are not archived; Power Platform snapshots contain only their validated allowlisted projection.

Package observations reject malformed or oversized facets, access-status strings, version markers and facet collections rather than shortening them or silently dropping entries. Accepted values remain exact; only display names and descriptions may be shortened, without splitting Unicode characters. NUL and unpaired Unicode surrogates are rejected before text/JSONB publication. Creation and modification timestamps must be valid, timezone-qualified ISO 8601 instants; their precision and offsets are preserved, while missing, null or empty timestamps remain unknown. Invalid observations fail with `provider_schema`, before inventory publication or mutation readback can accept incomplete state.

Package list/detail reads use Graph v1.0 and save only allowlisted complete observations for thirty days; refresh jobs are retained for seven days. Failed or partial refreshes never replace the last complete broad snapshot. Opening Agents with no saved broad snapshot starts one delegated read-only refresh per authorized session; other navigation reads saved data only. The Permissions first-page catalog check does not import inventory. **Refresh agents** explicitly submits and polls subsequent refreshes before reloading saved rows, including retries after a failed initial refresh. Provider-verified management readback publishes an exact saved observation while preserving the broad catalog snapshot and unrelated packages. Preview access and block/unblock use Graph beta and delegated `CopilotPackages.ReadWrite.All`; application permission is not supported. Microsoft documents global cloud and a Microsoft Agent 365 license, but no additional human Entra administrator role. Local serialization and immediate prestate hashing detect observed conflicts but cannot prevent an external administrator's change after the final read. In particular, the full access payload has no documented ETag/`If-Match` or equivalent lost-update protection and can overwrite a concurrent external change. Owner reassignment has no implemented product workflow or documented owner readback. [docs/mutation-canaries.md](docs/mutation-canaries.md) defines optional principal-separated qualification and restoration; evidence is recorded only after an approved cycle is restored and verified.

When typed bot fields are omitted, it also accepts the corroborated combination of the same environment, exact schema name and inventory native GUID equal to the source-declared CDS bot ID. A name or GUID alone is never enough. Conflicting fields, disagreements between package representations (including schema names), multiple candidate resources, malformed metadata and cross-environment matches remain unlinked. Schema names are compared case-insensitively and may be absent for typed-ID links, but a supplied malformed schema name in either source is not treated as absent.

Schema disagreements for the same declared environment/CDS identity remain conflicts even if only one representation matches inventory, and cannot qualify a control ID. Partial metadata containing only an environment or schema name still constrains declarative-manifest and custom-engine associations; it is not an identity proof by itself. Source-only declarative packages with distinct declared environments remain separate even when their manifest IDs agree.

Custom-engine association checks every independently matched resource, including Entra-agent and Entra-application matches, before attaching an otherwise unlinked package. When a shared bot application spans distinct matched resources, unproven aliases remain ambiguous while direct links stay intact. A CDS/native anchor is still required to extend a link; secondary identity matches alone do not become anchors or control-ID proof.

This inner metadata schema was observed in provider responses; it is **not a publicly documented package-to-Power-Platform identity contract**. Evidence is marked `source_declared_metadata` and retains element IDs and field paths alongside source observation metadata. Matching names, equal manifest/native GUIDs, shared blueprint IDs and associated application registrations are not sufficient to consolidate agents. Linking never grants permission.

Retained detail metadata is reused across an older-style broad summary only when a valid unchanged provider modification time and unchanged identity/version markers establish the same package revision. A completed identity collection or newer exact observation that omits metadata does not resurrect an older link. Source-qualified detail links resolve to the combined agent independently of the current page, preserving environment identity even when native IDs repeat.

The checked-package count measures completed detail collection, not successful identity matches. The count and matching explanation use the same collection evidence, including legacy exact observations and retained details. When a collected package has no `AgentMetadatas`, its matching explanation reports missing provider metadata rather than directing the user to repeat already completed collection. Sync also exposes conflicting and ambiguous identity counts; source-only records are not, by themselves, evidence of missing inventory.

Bulk-operation reference searches filter unified rows before pagination using the current tenant and principal's package audit targets. The lookup reuses the inventory transaction's database connection rather than acquiring another connection while holding the snapshot. A linked row is included when any of its packages matches; references do not reveal another user's operations or turn Power Platform resource IDs into package control targets.

Every full agent refresh now enumerates the catalog and collects exact details for every package in batches of four, within a 15-minute execution deadline and the existing 5,000-package/100-list-page limits. Sync shows identity progress, and cancellation, authorization revalidation and atomic publication cover the entire collection. A failed batch retains the previous complete snapshot; a successful exact 404 records absence. Selected-detail refresh remains available for 1-100 targets with its 120-second bound.

Package refresh capacity counts each pending or running job once, up to four jobs. The five-job per-principal admission limit counts only unfinished jobs still within their dispatch and retention deadlines; retained expired jobs do not block a fresh refresh. Cancellation and sign-out also stop jobs still acquiring authorization; sign-out does not wait under the account-session lock. Shutdown rejects new starts and drains pending starts as well as active collection before closing persistence.

Package reads retry transient HTTP 500/502/503/504, connection/body transport failures and individual read timeouts, at most three attempts with bounded backoff. Inventory reads share a start-rate gate with at least 250 milliseconds between requests across concurrent jobs. HTTP 429 and HTTP 424 responses explicitly reporting "too many requests" trigger a shared cooldown and up to six attempts with 30/60/120-second fallback backoff; other 424 failures are not retried. Provider `Retry-After` takes precedence, and Sync records the cooldown and retained identity progress. Caller cancellation and the overall job deadline stop retries and cancel default backoff timers; malformed/oversized responses and mutations do not retry. Terminal refresh failures retain the sanitized HTTP status, provider code and request ID in Sync and structured Docker logs, without exposing provider messages or definitions. Do not clear saved data to fix a failed identity collection: retry the ordinary refresh from Sync, retaining the last complete inventory until replacement succeeds.

For existing saved inventories without collected identities, opening Agents with current delegated read authorization starts one durable, idempotent identity collection per source snapshot, or follows an already-running broad refresh. It continues across tabs without opening a modal. Failed/cancelled collection is not automatically restarted; retry deliberately from Sync. Catalog GET/filter requests themselves remain saved-data-only.

The catalog has one row and one selection checkbox per verified agent, including all of its published package versions. **Manage** opens access, installation/block and quarantine controls together. Overview presents administrative information; source/link diagnostics remain under technical details and can optionally be enabled as table columns.

Package block/access and Copilot Studio quarantine remain distinct actions with separate state, permissions, confirmation and readback. Native targets are preserved. Quarantine requires a fresh inventory environment/CDS-bot identity; if its typed bot field is missing, the server can qualify the explicit Graph CDS bot ID only using the corroborated environment/schema/native-ID match and same-principal, current identity evidence no older than 24 hours. The catalog and target picker use the same proof as server preview/submission. Neither a frontend inference nor a generic "Disable" action substitutes for those checks.

A full observed or processed count does not turn a failed or inconclusive outcome into success. Sync runs and their underlying source jobs are separate, non-additive records.

Jobs is a bounded recent projection, not a complete audit archive: at most 100 records overall, up to 20 from each ordinary source, and up to 50 CSV staging records created in the last 24 hours. Accepted CSV entries open their exact read-only **Sync > Manage reports** snapshot inspector when recorded, or Manage reports history when no snapshot is retained; only active drafts open **Sync > Import reports**. Retained report bundles and administrative events remain in **Manage reports** and **Audit**, respectively. Provider result rows and detailed diagnostics remain in their authorized source views. Unavailable sources are named without discarding other records; failed reads do not appear as successful empty history. Automatic status polling pauses after five minutes of ongoing work and explicitly offers Refresh status.

Viewer may create, resume and cancel their own delegated read jobs, including package and Power Platform refreshes, but not operate imports, provider changes, mutation qualification, configuration, or mutation-job controls. Admin adds those supported administrative controls without widening principal-private caches. Recovery uses the existing action metadata, exact job ID and backend role/capability checks; uncertain-write reconciliation is read-only, and cancellation does not undo already dispatched work.

Purview and Defender search metadata does not prescribe one fixed capability: their forms check the selected authorization mode, and their backend services enforce that mode's current authorization and scope. Qualified application searches do not also require delegated readiness. A null capability in these action entries is not an authorization bypass or permission to fall back between modes.

Permissions keeps optional Admin-configured modes in a separate **Shared application modes** view with explicit active/inactive counts. Disabled modes are excluded from health and needs-attention counts. Once enabled, an application mode participates normally—including as degraded/not-configured until shared scope is approved—but never becomes an automatic fallback. Overview counts follow the selected permission scope; the header health indicator covers account capabilities and enabled shared modes.

Defender hunting needs no separate delegated approve/run qualification ritual. A Viewer or Admin submits one explicit bounded hunt; the actual request establishes provider evidence for that principal and exact tuple. Ordinary delegated jobs have no retained-scope binding and remain tenant/principal-private, including from other Admins. Optional delegated qualification APIs may remain but are not prerequisites. Automatic permission checks acquire only `ThreatHunting.Read.All` token evidence and never run KQL, prove license/data-source visibility or create a hunting job. Application/shared-scope configuration, qualification and retained-scope revocation are Admin-only. Application mode requires explicit Admin opt-in, shared-scope approval and application qualification; there is no automatic fallback. See [docs/defender-agent365-hunting.md](docs/defender-agent365-hunting.md) for source/projection allowlists, dynamic-detail limitations, job bounds and the `rootSpanObserved` boundary.
