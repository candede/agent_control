# Agent Control

Agent Control helps administrators understand and manage their organization's AI agents in one place: discover agents, understand adoption and user-agent relationships, investigate activity, and take supported access-control actions. It uses Express, React, Microsoft Graph and the Power Platform Resource Query API. One Node process serves the API and built UI; PostgreSQL owns sessions, on-demand and signed-in refresh jobs, private inventory snapshots, minimized Purview audit-search results, official Microsoft 365 usage reports and append-only administrative audit.

The original [13-phase plan](plans/admin-poc-production/README.md) records the runtime, persistence, identity/capability contracts, Permissions, saved package observations, fenced mutations, official usage imports, bounded Purview/Defender searches and exact Copilot Studio quarantine controls. The [agent-centered roadmap](plans/agent-centered-power-platform/README.md) replaces its standalone Power Platform catalog with agent-only workflows and supporting environment context. The canonical `/agents`, `/users`, `/sync`, `/audit` and `/permissions` routes are served by the same Express artifact. Retired `/jobs` bookmarks open Sync; task status and recovery stay with their originating workflow. Security investigations now start in **Agents > agent details > Activity**; retired `/security` bookmarks return to Agents without restoring pasted IDs or broad hunts. The retired Power Platform route is not redirected or migrated; the unrelated `/official-usage` bookmark migration still opens report workflows in Sync. No live package or quarantine canary, quarantine status read, Purview lifecycle or Defender query was authorized during the original phases in the unconfigured local environment; this is missing live evidence, not a prerequisite for ordinary operations. Implemented package access, block/unblock and quarantine changes run on demand for an authorized, confirming Admin. Owner reassignment has no implemented product workflow or documented owner readback. No transcripts, continuous event collection or raw archives are implemented.

## Unified Workbench

The six canonical views use two hierarchical roles. `AgentControl.Viewer` can observe every view, including exact targets and assignments, user-level accepted reports, agent-scoped investigation results, and local administrative audit; it can run and cancel its own delegated read, refresh, search, and export lifecycle. Explicit delegated Purview/Defender requests establish their own principal evidence without a separate qualification ritual. `AgentControl.Admin` includes all Viewer access and adds supported changes, imports, configuration, mutation and application/shared-scope approvals, and mutation-job controls.

- Agents represents each resolved logical agent once in a tenant/account-private canonical registry, not once per API result. Several catalog packages can belong to one native agent without losing their separate access/block targets; the same row also retains Power Platform configuration and eligible quarantine controls. Reconciliation serializes with source publication and runs before filtering, counts, or pagination. Publication carries existing source memberships forward without inheriting old matching proof, so retention before the next read does not discard unchanged canonical identities. Canonical `agent:<uuid>` links remain stable across ordinary refreshes; exact package and environment/native links resolve to the containing row. Power Platform collection includes only agents and environments supporting their context, not standalone apps, flows, connectors or environment-group records.
- The Agents workspace uses a compact app bar, source tabs beside the page title, and one source-qualified summary strip above the table. The strip shows **Agents in catalog** (or the selected inventory scope), **Available to end users**, distinct reported-used agents in the selected report set, and agents in that set reported active in the last 30 UTC calendar days. Inventory membership includes agents that users cannot access; end-user availability requires an unblocked package available to all or some users and no known native quarantine, across hosts (not just Teams). Creation, installation, publication and past use alone do not qualify. The first two summaries clear table filters and show their matching lists. Inventory counts cover the complete authorized saved inventory before filtering/paging, with partial coverage noted in the strip. Report counts include identities absent from saved inventory and must not be added to inventory totals. Admins switch the shared reporting set immediately through **Report context**, beside the reported counts rather than the inventory source tabs. Each set's dates are labelled as a supplied reporting window or observed activity dates, never inferred complete coverage. Selected-report dates also appear in the table toolbar when usage columns are shown. Agent details use four strictly agent-scoped tabs: **Overview**, **Usage & users**, **Manage**, and **Activity**. Retired `package` and `power-platform` detail-tab aliases are no longer supported.
- Overview groups **Responsibility**, **Environment**, **Configuration**, and **Configured connectors and operations**, alongside the full sanitized description and status/access facts. Owner, creator and last modifier remain distinct from access assignments, operation creators and reported usage. Environment name, region, type, managed state and group come only from exact current saved environment identities in the same tenant/account scope, with their own observation date; unavailable facts stay unknown. Opening Overview or Manage reads authorized saved package details without refreshing providers. Multiple published versions retain their exact selector and management targets; native configuration has its own observation and does not pretend to describe the selected Graph package version.
- Configured connectors and operations come only from the documented agent-embedded Resource Query fields: usage as Tool/Topic Tool/Knowledge, enabled state, end-user consent, Maker/User connection provider, invocation conditions and the operation configuration creator's exact ID. Reported totals are separate from bounded saved details (up to 200 connectors and 200 operations). False and zero are preserved; missing, malformed, capped and contradictory details remain unknown or partial. Long connector lists are paged without reducing totals. Preview connector metadata reflects published agent structure, not unpublished changes or observed executions. Arbitrary JSON names, URLs, hosts and plugin references are not presented as native dependencies.
- Invoked-flow relationships are **unavailable from synced sources**, not an empty flow list: Resource Query and Graph package/declarative/plugin schemas do not establish native invoked-flow identities. No Dataverse integration or standalone flow/connector catalog is added. Overview offers clearly labelled, fixed-origin Microsoft console landing links; these are handoffs, not exact deep-link guarantees, relationship proof or management authorization. Source IDs and provenance stay under disclosure.
- Manage embeds the **Available to / Installed for** editor directly: scope choices, directory picker, assignments and Apply are part of the agent modal, not launcher buttons or another editing screen. Block/Unblock sits beside the exact selected version; eligible quarantine remains a separate control. Directory names are resolved only for the active setting when permitted, while Viewers can read saved assignment IDs without directory or write access. Apply refreshes the exact package before requesting its server-issued preview; access and block confirmations appear inside the same agent modal. Cancelling confirmation preserves the draft, settings have independent drafts, and changing versions cannot carry a draft to another target. Successful access changes reload saved settings. The standalone and bulk editors reuse the same form. Source IDs, link evidence and raw diagnostics remain under technical details.
- **Agents** owns current agent usage, while exact source-snapshot tenant totals and report-only agent comparisons remain in the read-only **Sync > Manage reports** snapshot inspector; reported-user breakdowns are available in **Users**. Agents automatically matches a reported Agent ID to the exact full, case-sensitive Graph package ID in the viewer's authorized current saved inventory, then uses its existing canonical membership, including any established Power Platform link. Names, GUID fragments, manifest IDs and Entra application IDs are not alternative report keys. The table, **Usage & users**, sorting, filtering and export share this read-time projection; no manual setup, provider calls or association writes are needed. Opening an agent modal never fetches tenant report candidates or renders tenant totals. Missing matches remain unavailable, not zero. Existing explicit reviewed associations remain labelled report-set-scoped overrides; automatic matches are labelled exact package-ID matches, not administrator reviews. Reported-user links retain the exact report identity and set. Stale reports, inferred activity ranges, missing data, and source-total disagreements remain visible. Usage attribution never grants management permissions or creates native identity links.
- Users offers three separate cohorts: **Paid M365 Copilot users**, **Active users without paid Copilot**, and **Agent responsibility**. The license dashboard defaults to effectively **Licensed users**, including people without matched usage. Its adoption cards require verified active paid features, not just a containing product assignment, basic Copilot Chat access or recent usage. Active nonpaid users require current saved license evidence and reported activity; report filters, rankings, retained snapshots and CSV semantics remain separate. An explicit `0` differs from missing evidence. Detailed directory/report context requires an existing unique saved link for the exact report set and versions; unresolved, concealed or historical report identities are not matched by display name.
- **Agent responsibility** includes native owner, creator and last-modifier identities outside the paid/report rosters, using current authorized saved agents and the existing private people cache—never a tenant-wide directory sync. Search and pagination follow complete canonical reconciliation of both bounded saved sources, not just the first 250 agent rows. A person can have multiple distinct roles on shared or Power Platform-only agents. Missing/invalid fields, unavailable/partial sources, unverified identities, not-found and failed lookup evidence remain explicit. No reported relationships is not proof of no responsibility elsewhere. License and usage are not inferred from responsibility, and responsibility grants no control access. Agent Overview opens an exact resolved person's `/users?view=responsibility&person=<object-id>` context; user responsibility opens the current canonical agent's Overview. Invalid/unresolved agent people are not linked to guessed profiles. Paid/report details also show responsibility only when an exact saved directory ID is established. All browsing uses saved reads and cancels/clears across identity or permission changes.
- **Sync > Import reports** and **Sync > Manage reports** replace the standalone Official usage page. Manage reports owns one paginated retained-history table, with Admin actions and read-only Viewer viewing, plus import lineage and deduplication accounting. Its deduplicated cross-import agent locator preserves exact report identities absent from newer imports or saved inventory; it does not repeat the cumulative summary cards on Agents. Optional UTC date filters select observed agent last-activity evidence, not reconstructed daily response totals. The snapshot inspector retains unique source evidence, exact tenant response/user measures, raw report-only rows, comparisons, and agent CSV exports for one exact bundle; overlapping rolling-window totals are never added. Current agent usage belongs to Agents, licensing and user activity to Users, and collection/import/report management to Sync.
- Adoption insights retain contextual links to the exact reported agent and source snapshot inside Sync, rather than generic Users or retired-page shortcuts. Missing-report guidance points to the existing primary navigation.
- An agent's **Activity** tab owns contextual Defender/Agent 365 hunting, exact saved Purview records, and saved source observations. The server resolves supported typed identities from the selected authorized agent; there are no agent-ID text fields or standalone Security page. The modal preserves bounded templates/date/operation filters, history, row details, CSV, qualification and lifecycle controls. Purview browsing filters only exact retained bot/environment records, not a speculative live tenant-wide search. Enterprise-application object IDs and telemetry application/client IDs are separate; missing or unverified runtime mappings stay unavailable rather than being guessed. Missing evidence does not imply zero usage or safety. Microsoft portals retain broad hunting, incidents and compliance workflows; the Audit view retains local administrative history and existing user-oriented audit workflows. Opening Activity never starts a provider hunt. See the [capability research and integration boundaries](docs/defender-agent365-hunting.md). Inapplicable quarantine controls are not promoted for package-only agents; all eligible controls retain exact-target confirmation and authorization checks.
- Sync (`/sync`) groups data collection, source coverage diagnostics, exact matching-detail refreshes, Power Platform agent refresh/export, and retained sync history. Agents keeps a compact count and partial-coverage indicator; package and quarantine bulk controls appear only for a selection or retained work. Select packages on Agents before opening Sync to refresh their matching details; tab navigation preserves the selection and filters.
- Agents keeps Search, **Show agents**, **Filters**, and **Columns** in a single desktop table toolbar. Filters opens an on-demand panel containing Built with, Assigned access, Host, Publisher, Package status, Created within, environment search/selection, and sorting. Changes apply immediately. Escape or Close filters dismisses the panel and returns focus to its trigger; clicking or tabbing outside also dismisses it. Active restrictions remain visible as individually removable chips, including on bookmarked/history-restored routes, without reopening the panel or permanently pushing the table down. Environment search narrows the choices; selecting applies the filter. Choices come from the complete authorized saved inventory, using saved names when available and explicit unnamed-ID labels otherwise. Source and link-state filters remain removed, including obsolete URL restrictions, while exact agent and job links remain valid. Built with and creation age include saved Copilot Studio agent properties, regardless of package presence; package status, publisher, availability, and host still require matching saved package properties and do not infer missing values. Clear filters and Reset filters preserve sorting. Column headings also sort directly. Export and saved-inventory freshness sit beside the Agents heading.
- Built with filtering uses the same canonical authoring labels as its choices, including provider spellings displayed as Copilot Studio. Modified sorting compares actual instants across saved package modification and Power Platform publication/creation times, using the latest instant in each grouped row before pagination. Equal instants use the exact row ID as a tie-breaker; undated rows remain first for oldest-first and last for newest-first sorting.
- Identity matching distinguishes Studio environment/CDS/schema identities, declarative manifest identities, and custom-engine bot application identities. Declarative packages link only when their manifest ID agrees with both the native ID and GUID schema name of one authorized agent resource. Custom-engine package representations can share one row when their declared bot application identities agree and the native association is unique. Equal names, package-management app IDs, or blueprint IDs are never merge evidence. Source-specific Graph and Power Platform agent identity IDs can differ even when the exact native agent agrees; this difference is retained as a diagnostic, not a false native-identity conflict. Ambiguous native/environment claims stay separate.
- Source details show exact identifier kinds, observation times and authorized related observations. Links distinguish corroborated source metadata from a documented Microsoft identity guarantee. A manifest, bot application ID, name, package ID, blueprint, or Defender ID never becomes a CDS quarantine target. An alias package cannot refresh another package's expired native-control proof. Official usage is authoritative only from the three companion Microsoft exports.
- Task status stays in its workflow: Sync history, CSV report management, agent-control progress, or entity investigations. Interrupted package controls offer **Resume unprocessed tasks** beside progress and cancellation on Agents; uncertain writes offer read-only reconciliation, never replay or automatic inverse operations.
- Package access labels, mutation preparation and provider readback share status normalization, including the existing `deployedToNoOne` and `deployedToNone` compatibility spellings. The combined **Allowed for Some or All** inventory facet and filter use the same aliases, ignoring case and separators in both saved-package SQL and unified inventory filtering. Raw provider status strings, including future values, remain unchanged in responses and exact-value filters. Explicit scopes take precedence over principal entries; missing or unknown status still uses the existing principal-based fallback and remains unknown when no principals are present. Adding access from an explicit **No users** scope assigns only the requested principals, without reactivating inactive entries returned in that collection; the unselected setting remains unchanged. Confirmation, dispatch and readback use the same rule. Package inventory rejects malformed collection pages and continuation links rather than treating them as a complete snapshot.
- Downloads are authenticated server exports tied to an exact saved selection. Agents exports one row per logical agent, retaining every associated package and the observed native configuration. Each package-state entry retains its exact ID and version; a missing version remains `null`. With no selection it exports all filtered pages, including organization/usage and environment filters; exact canonical/package/native selections are resolved and deduplicated on the server. Column visibility does not remove approved CSV fields. A scoped saved-source and usage revision fences refreshes, exact overlays, environment changes, report selection/deletion, reporting associations, expiry and cleanup; audit-reference filters are separately revalidated. Inventory exports are capped at 5,000 rows, official exports at 100,000 output rows, Defender at 200 rows, and local administrative audit at 100 exact selected events. CSV generation is bounded to 8 MB (2 MB for Defender; 1 MB for local administrative audit), with a 15-second publication deadline and disconnect handling. Oversize selections fail rather than silently truncate. Current session, role and source validity are checked again before publication; stale scope, deletion or revocation stops the download.
- CSV formulas are neutralized and only approved fields leave the server. Audit records source/selection/count metadata, never exported rows. No export file, bearer link, original CSV archive, transcript viewer or maintenance console is created.

The local workbench can show truthful setup/disabled states without live provider credentials. Deterministic browser fixtures are isolated test tooling, not qualification or a production sign-in bypass. See the [Phase 10 completion](plans/admin-poc-production/completions/10-unified-admin-workbench.md) for exact tested commands and retained-environment evidence.

It rejects paths and CLI arguments. Set the existing loopback base URL, test-only fixture mode, isolated PostgreSQL and repo-local evidence directory as usual. ## First-use data sync

Data sync coordinates saved Microsoft 365 Copilot entitlement evidence and app-activity data, Graph packages, and Power Platform resources. The Users count is **directory users checked**, not effectively licensed users or tenant headcount. Graph filters the whole tenant for products containing paid Copilot features and returns per-user feature evidence in pages, so the app does not need one license request per user. A 30,000-account tenant may legitimately have only about 4,000 matching candidates and fewer effectively licensed users, because bundled Copilot features can be disabled. Official usage CSVs have a separate import workflow. First use is based on persisted synchronization state, not an empty table: an authorized scan that finds zero objects is different from a source that was never queried, failed, or requires permission.

Users derives effective paid **Microsoft 365 Copilot licensing** from verified active paid features, not the state of a containing product or SKU. Standalone and bundled Copilot follow the same service-plan rules; an assigned product with no active paid features qualifies for neither a positive licensed label nor paid-license adoption counts. Paid-feature labels distinguish active, grace period, not enabled, suspended, locked out, unverified and partially active. None means that basic Copilot Chat is disabled. Directory paging allows 1,000 pages with the existing 100,000-observed-row bound and requires every matching page to reconcile with Graph's counts; incomplete collections are never saved as complete. Migration 37 deletes the app's old cached Users-sync data and resets its saved counts once; run Users sync after applying that migration. The effective-entitlement correction and paging fix add no migration or reset of current-format snapshots. See [Paid Copilot license detection and usage](docs/copilot-license-usage.md).

For official usage, an Admin exports the **Agents**, **Users & agents**, and **Users** CSVs from Microsoft 365 admin center **Reports > Usage > Microsoft Copilot > Agents** using the same 7- or 30-day selection. **Sync > Import reports** opens a dedicated modal wizard: **Files > Validation > Review & accept > Result**. Report management and legacy-browser cleanup are separate from this approval flow. Reports remain unavailable until a complete validated bundle is accepted, but do not block automatic inventory/user sync. Viewers can synchronize their own authorized read sources; acceptance still requires Admin. Existing accepted reports are preserved during a full resync.

Open the **Sync** tab for **Inventory health**, **CSV usage reports**, **Data sync**, and **Sync history**. The CSV section owns **Add CSV reports** and **Manage reports**. Its **Observed activity dates (UTC)** are calculated automatically from the earliest and latest activity dates across all three report kinds in all retained complete report sets, not just the current selection or latest upload. No manual reporting dates are needed. Undated reports are identified explicitly; the range may contain gaps, and overlapping usage totals are never added. The summary updates after report acceptance, selection or deletion and can be refreshed without starting a sync. First use adds a **Setup needed** hint without opening a modal or redirecting other pages; session-driven automatic refresh can collect missing sources in the background. **Workspace data** always shows all three automatic sources and their last successful counts/times, independent of the latest or selected run. A users-only sync does not replace Graph or Power Platform state; a failed attempt does not turn its observed count into a saved total.

### Automatic refresh while signed in

The visible, online workbench checks for due work approximately once a minute and when returning to the app, regardless of the selected page. The automatic-refresh status banner appears only on **Sync**, not Agents, Users or other pages. The CSRF-protected `POST /api/data-sync/auto-refresh` uses the current delegated account; it is not an app-only collector or an unattended server timer. The backend deduplicates admission across browser tabs and processes. Saved-data GETs remain provider-free.

Active browser checks and saved-data reloads use a small, non-interactive rotating icon in the corner, with no visible text, shown only when a request lasts more than half a second. It disappears when those requests settle, even if server-side sync or detail enrichment continues; long-running job status stays on **Sync**. The icon remains labelled for assistive technology and stops animating for reduced-motion preferences. Users keeps the last successful counts, rows, filters and open details visible while the same view refreshes; routine reads do not turn verified snapshots into loading or unknown states. New snapshots replace the displayed data when ready. Actual read failures, unavailable source evidence and revoked access retain their existing warnings and access safeguards.

- **Every 15 minutes:** refresh due directory/Copilot license evidence, the paginated Graph package catalog, and Power Platform agents/environments. Automatic catalog publication does not wait for a detail read for every package.
- **Hourly detail enrichment:** independently refresh bounded batches of package details, prioritizing new, changed, and missing details. Detail observation times remain separate from catalog freshness. This is a scheduling target, not a guaranteed completion SLA under throttling.
- **Every six hours:** refresh the Copilot app-activity source when due, rather than downloading it with every directory scan. Automatic owner/creator enrichment reuses the existing reference cache.
- **On demand:** manual full/source sync and fresh management prestate/readback checks remain available. Official agent-usage CSV reports remain manual.

Automatic refresh never clears saved data, imports reports, runs hunts, or dispatches management actions. It defers to an active manual sync. Failed attempts retain saved data and back off; permission/authorization failures remain visible. Hidden/offline pages and paused sessions do not admit more work, while already-started server jobs retain their normal cancellation and authorization checks. Sign-out, account changes, and shutdown stop provider work through the existing fences. Restart does not silently resume a collector without a new signed-in request.

A successful sign-in makes older authentication-blocked automatic work eligible for one fresh attempt on the next check, without waiting out its hour-long cooldown. Reloading the page or rechecking permissions does not bypass that cooldown. Ordinary job startup is shown as refreshing, not as a sign-in failure. Missing read permissions or provider roles are shown separately under **Permissions**; signing in cannot grant them. Detail-enrichment authorization failures back off for the whole detail lane instead of repeatedly trying new batches. Other eligible sources continue, and saved data is retained.

Apply migrations **45 and 46** with the matching application through the existing operator deployment/migration process. No reset or new provider permission is required.

Active collection has a prominent progress panel with queued/running/blocked source states, real per-stage observed counts, source messages, and update times. Its bar measures completed automatic sources, not elapsed time or a guessed total-object percentage. Counts are not added across different source types and can restart when collection enters a new stage. Completed runs have a compact, explicitly scoped result, while overall workspace counts stay visible. **Check status** only reloads status; it never starts collection. Live status updates continue for active runs without a time limit or a pause/resume step.

**Sync history** combines sync runs and Graph / Power Platform refreshes in one table, newest recorded start first, with scope, outcome, explicit result units, and duration where recorded. One outcome filter and pagination cover the combined bounded history, not a complete audit archive. **View details** preserves exact run dialogs and standalone or underlying refresh links without substituting historical results for workspace state. Runs and their underlying refreshes are separate records, not additive totals. To collect again after an incomplete run, start a fresh sync with the normal Sync action; old runs have no retry-incomplete controls. This does not require clearing saved data. CSV snapshot history is in **Sync > Manage reports**. Old `/jobs` bookmarks open Sync, and `/agents?syncRun=...` bookmarks redirect to `/sync?syncRun=...`.

**Inventory health** near the top of Sync explains source errors, pending or invalid package metadata, and conflicting identity links without opening a dialog. The Agents attention notice uses the same checks. A completed catalog sync can still have details awaiting separate background enrichment; it does not mean all identity links are verified. **View diagnostics** contains the detailed receipt and source-specific repair/export tools. It is not an additional approval step. Routine collection and CSV import do not require opening diagnostics.

The three collection actions are:

- **Start initial sync** collects users and inventory for first-use setup without deleting saved data.
- **Sync all sources** reads the latest users and inventory, keeping previous successful snapshots until replacements are ready. Each source row also has a scoped **Sync** action.
- **Reset saved data...** opens a separate confirmation requiring acknowledgement, then clears only the current tenant/account's saved users, license/app-activity snapshots, Graph packages, Power Platform inventory, and their synchronization success markers before a full read. These views can be empty until collection succeeds; failure or cancellation does not restore cleared data. Accepted usage reports, report history, audit records, configuration, jobs, and other accounts' saved data are preserved. It is not a database reset and does not change Microsoft settings.

Provider reads run in durable source jobs. Switching tabs does not cancel or restart them; return to **Sync** to check progress. Retry resumes incomplete sources without replaying successful collection, and restart or sign-out requires renewed authorization before more provider work. Cancellation, sign-out, and shutdown join pending admission and source work before reporting completion; overlapping retries of the same run are rejected. An expired retained child job does not prevent cancellation or an explicit retry of its incomplete source. New default initial, incremental, and full runs include only the three automatic sources. Explicit `usage_reports` requests and retained older runs with manual steps remain supported; finish their import or cancel the waiting run before starting another run. API full-resync requests remain nondestructive unless they explicitly opt into `clearSavedData: true`.

Retry controls wait for running collection to settle and remain disabled while a different run is running or waiting. Incomplete sources on the same waiting run can still be retried.

The Sync page's current run, exact-run dialog, history, and linked package-job status keep polling until the observed work stops progressing; there is no elapsed-time cutoff. These requests only read saved backend status, never Microsoft Graph. Reads remain non-overlapping within each polling cycle, and errors and authorization loss are surfaced rather than treated as completion. Unmounting or changing the account cancels owned requests and timers without cancelling server jobs. The current-run and exact-run observers also keep refreshing saved views when another workbench tab is selected. Browsing retained runs does not stop current source completions from refreshing saved views, and status reloads preserve change detection for the selected run. Changing the selected run during an action still checks saved status afterward, including when the action response is lost, without replaying the action or replacing the selected historical run. Backend execution deadlines and provider throttling policies are unchanged.

The current run follows the most recently updated run, including retries of older runs; retained history stays ordered by original start time. Overall source state comes from persisted success markers, not that run's scope or progress. When a saved-status read reports cleared sources, saved-view invalidation also covers failed attempts that retained snapshots and sources omitted by a prior limited run, including recovery after a lost clean-resync response.

Initialize a **fresh development database** through schema version 46 and apply runtime grants before starting this agent-centered runtime. The Power Platform definitions in versions 5 and 33 now enforce the two-type contract directly; existing broad-catalog databases are not an in-place upgrade target. There is no compatibility migration, old-data backfill or dual reader for that retired catalog. Use only an explicitly owned disposable database/project, never a shared installation, for fresh initialization. The retained migration lineage supplies canonical entities and scoped source memberships (32), actual queried-type metadata (33), reviewed usage associations (34), saved agent people (35), automatic-source clean-resync admission (36), current Users cache format (37), and paired access-canary qualification (38). Current-lineage databases can apply the additive package enrichment (45) and automatic sync (46) migrations normally; no saved-data reset is needed. Verify readiness as `agentcontrol_app`, not the operator: associations permit `SELECT`, `INSERT` and `DELETE`, while association revision state is read-only to the runtime. Within the current schema, clean resync clears that account's canonical inventory together with its source snapshots, and rejects unfinished standalone package or Power Platform refresh jobs without deleting data; finish or cancel those jobs first. Clean resync is not a schema conversion.

Package identity metadata is parsed and its native fields are validated before storage, so a large authoring definition cannot cut off its native IDs. Complete package element definitions are retained within the provider/storage byte budgets rather than slicing JSON. They support documented package configuration and exact identity matching, not heuristic native connector or flow relationships. Malformed or oversized observations fail explicitly. Sync reports invalid matching details separately from identities checked; refresh the affected packages or run a confirmed clean resync to replace failed observations. Rebuilding the canonical registry within the current schema does not require resetting the database or removing accepted reports.

Saved user/license and app-activity reads remain tenant/principal-private. Current accepted agent-usage reports are joined when those saved users are read, so a new report import does not require another Graph scan. Audit Search and Defender remain separate, bounded, explicitly requested investigations; onboarding does not claim to collect unlimited logs or transcripts. Management actions continue to revalidate live authorization and exact target state independently of saved inventory.

## Local Deployment

Host prerequisites: PowerShell 7, company-approved Docker Engine/Desktop with Compose v2 or newer, and a browser. Node, npm, Vite, PostgreSQL, tests and browser automation run **inside Docker**. Initial onboarding requires an approved Entra application's tenant ID, client ID, client secret and explicit accepted username domains. Each configured tenant can use its own single-tenant registration. No Azure subscription or Key Vault is required for local deployment.

Local deployment does **not** load a repository `.env` file. [deploy-local.ps1](deploy-local.ps1) accepts the commands `start` (the default), `stop`, and `edit-config`, positionally or via `-Command` / `-Action`, plus `-Project` (default `agent-control`). The optional `-DbReset` switch (also spelled `-db-reset`) is valid only with `start` and explicitly requests a fresh application database. After software preflight, first start or missing settings trigger a wizard for tenant credentials, accepted domains and local port (default `3001`). Configuration is saved in the fixed repository-root `.local/<lowercase-project>/` directory; custom state locations are not supported. Configured starts reuse saved profiles, port and optional public URL without prompting. The script regenerates `compose.env` for Docker Compose; do not edit that generated file.

From the repository root:

```powershell
pwsh ./deploy-local.ps1 start
# Omitting start is equivalent:
pwsh ./deploy-local.ps1
```

Open **http://localhost:3001**, or `http://localhost:<saved-port>` when configured differently, unless a public URL is saved; in that case open the public URL. Use this single canonical origin, not a second `127.0.0.1` browser origin. Every `start` first builds the operator and qualifies the software in a uniquely named, disposable Compose project. Its PostgreSQL uses memory-only fixture data, synthetic passwords, no application secrets and no external network. Backend/frontend tests, backend typecheck, frontend lint and the production build must pass, and fixture cleanup must succeed, before the runtime image is built or deployment enters maintenance. Without `-DbReset`, deployment then starts/checks PostgreSQL and performs a **read-only migration-history preflight before changing maintenance or stopping the app**. Only a compatible schema proceeds to app drain, serialized forward migrations and app startup, waiting up to 90 seconds for readiness. A software/build failure leaves the existing app, database and maintenance state unchanged; a database-preflight failure leaves app and maintenance state unchanged and applies no migrations. Normal deployment never resets data; failures return nonzero without announcing success. Two long-running services remain: `app` and `postgres`.

`database_schema_incompatible` identifies an unknown or changed applied migration and its version. Do not rewrite stored migration checksums or expect another ordinary `start` against an incompatible database to repair it. For an intentional fresh development database in the **same project**, run:

```powershell
pwsh ./deploy-local.ps1 start -Project agent-control -DbReset
```

**This deletes all application database contents**, including imported reports, audit history, jobs, saved inventory and sessions. ### Local Secrets

State is always the ignored repository-root `.local/<lowercase-project>/` directory; there is no custom state-root option. Directories are mode `0700` and files `0600` on Unix; Windows uses an explicit current-user ACL with inheritance removed. Keep the state directory with the retained Docker volume in your recovery inventory.

| Relative path | Format / lifetime | Mounted consumer |
| --- | --- | --- |
| `secrets/postgres-admin` | 48 random bytes, 64-character Base64; generated once | PostgreSQL bootstrap and disposable operator only |
| `secrets/postgres-app` | Independent value, same format; generated once | Bootstrap plus restricted app login |
| `secrets/session` | Independent value, same format; generated once | App session-cookie signing only |
| `secrets/tenants.json` | Protected array of tenant profiles, including credentials and explicit domains; mounted as `TENANTS_JSON_FILE` | App; never a build input |
| `secrets/client-secret` | Legacy input retained unchanged after migration; not used by the migrated runtime | Migration/recovery only |
| `settings.json` | Non-secret `tenants` metadata, port and optional public URL | Local script |
| `compose.env` | Non-secret paths, image names, port, UID/GID, origin/callback and proxy trust; no registry JSON or credentials | Compose |
| `control/maintenance` | Presence closes new work admissions | App read-only mount |
| `control/reauthenticate` | Pending login-session purge after tenant/domain/application changes; processed on next `start` | Local script |
| `backups/` | Native dump plus count/hash receipt | Deployment operator only |

Secrets are file mounts, never image layers, build arguments or logged values. The runtime receives no admin password or operator code and has a read-only root filesystem, dropped capabilities and no Docker socket. It uses the host UID/GID locally to read restricted bind-mounted files.

Managed Compose calls temporarily remove project interpolation variables and registry/legacy identity variables (`TENANTS_JSON`, `TENANTS_JSON_FILE`, `TENANT_ID`, `CLIENT_ID`, `CLIENT_SECRET`, `CLIENT_SECRET_FILE`, `TENANT_DOMAINS`, `TENANT_DISPLAY_NAME`), then restore them, preserving unset versus empty values. The generated environment and protected mount remain authoritative. `LOCAL_TEST_IMAGE` selects the operator image only in the fixture environment. Empty values must not be used to clear overrides: Compose treats an empty `LOCAL_STATE_DIR` as an override and incorrectly resolves secrets under `/secrets/`. If an older script failed with that mount path, rerun `start` with the corrected script and the same `-Project`; retain the existing state directory and volume.

With an existing volume, missing or corrupt DB/session secrets **stop deployment**. Restore their original bytes from the same installation's protected state backup; do not generate replacements. A valid-looking but incorrect password also fails actual authentication. Back up the protected tenant registry separately from database dumps and restore matching tenant metadata; a lost migrated registry is never regenerated from legacy files. Database/session credential rotation is a coordinated operator action, not a deploy side effect. Coordinate origin changes with every Entra callback registration. The [configuration contract](docs/deployment-setup.md#tenant-registry-and-domain-routing) also documents direct runtime and Azure inputs.

## Lifecycle And Recovery

```powershell
pwsh ./deploy-local.ps1 stop
pwsh ./deploy-local.ps1 start
pwsh ./deploy-local.ps1 edit-config
```

Add the same `-Project` used at installation. `stop` leaves data and secrets intact; `start` always qualifies software with isolated tests before entering maintenance, then migrates and starts using the saved port. After a failed software check, fixture cleanup or image build, the previous runtime and maintenance state are unchanged; a preceding configuration edit may already have stopped the app. After a migration/app-start failure, maintenance remains closed; fix the reported target/configuration/schema problem and rerun `start`. Never remove the volume as a recovery shortcut. Health remains separate from provider availability.

Advanced testing, retention, backup, restore, reopen and whole-project destruction use existing **operator-only PowerShell helpers**, not arguments to `deploy-local.ps1`. Database-only reset is the explicit `start -DbReset` workflow above. See [the operator helper setup](docs/operations.md#operator-only-local-helpers), [retention](docs/operations.md#retention), and [backup/restore](docs/operations.md#backup-and-isolated-restore). There is no separate maintenance executable.

The internal `Backup` helper writes a new timestamped `.dump` and `.dump.json` under the protected project backup directory, using a PostgreSQL repeatable-read snapshot and `pg_dump` custom format. The receipt records SHA-256, schema and per-table counts/content fingerprints, not row contents. Its `-BackupFile` parameter selects an explicit new filename in an existing restricted directory. Existing files are never overwritten.

Restore always creates a **new isolated database**, never the source/default database. Follow the [operator restore and reopen procedure](docs/operations.md#backup-and-isolated-restore), selecting the exact project and an isolated target such as `agentcontrol_restore_check`.

`pg_restore` runs transactionally, followed by schema/count/content validation and explicit grants. Existing targets and changed receipts fail. A failed restore target remains isolated for review; the source is unchanged. Review retained data and run operator retention before any separately approved promotion. Phase 01 does not switch the running app to a restored database. After a successful check, remove only that exact isolated target:

```bash
docker compose --env-file .local/agent-control/compose.env -p agent-control exec -T postgres \
  psql -U agentcontrol_admin -d agentcontrol -v ON_ERROR_STOP=1 \
  -c 'DROP DATABASE agentcontrol_restore_check WITH (FORCE)'
```

Keep local dump/receipt pairs for at most **seven days** and remove expired pairs during routine operator maintenance (internal `Retain` helper). Keep secret-file recovery copies under the organization's credential policy, separately protected from data dumps. Database retention removes expired sessions, capability evidence and package mutation qualification records, seven-day jobs/items/attempts, expired package snapshots/refresh jobs, 30-day Purview jobs/results, audit older than 90 days, old import receipts and unused source identifiers. Expired authorization evidence cannot authorize provider work; expired optional canary evidence no longer proves qualification but does not gate ordinary writes. Run Retain at least daily while actively using this POC; it never calls providers. Backups have a finite lifetime, not an instant deletion guarantee.

Destructive reset is a separate, explicit [operator-only helper action](docs/operations.md#local-secret-or-volume-recovery), never a deploy step or public command.

This removes that project's containers, volume and local state including its backups. Back up anything needed outside that directory first. The exact case-sensitive project/volume confirmation is mandatory.

## Persistence And Jobs

PostgreSQL **17** is pinned in Compose. The fixed database is `agentcontrol`, operator login `agentcontrol_admin`, runtime login `agentcontrol_app`. Structural driver settings use `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD_FILE` (or injected `PGPASSWORD`); remote connections require TLS verification, while the private local container connection uses disabled SSL. Passwords are not concatenated into connection URLs. The app pool caps at four connections, 5-second connect and 15-second statement timeouts, with UTC timestamps.

[backend/scripts/database.ts](backend/scripts/database.ts) owns bootstrap, explicit checksum-verified migrations and grants. [backend/src/db/schema.ts](backend/src/db/schema.ts) defines schema versions 1 through 40. Migrations 5-6 own private Power Platform inventory; migrations 7-12 own package observations, mutation confirmation/readback/reconciliation, and finite canary qualification; migrations 13-15 own official usage staging, immutable publication, selection and exact retry receipts. Migrations 16-17 own Purview qualification, durable minimized results, scoped execution fencing and request budgets. Migrations 18-21 own Defender hunting, qualification and retained scopes. Migration 22 owns Copilot Studio quarantine observations, durable jobs/items/attempts, append-only audit, separate canary approvals and finite qualification. Migrations 23-25 extend the allowlisted administrative-audit actions, migration 26 adds singleton operational state, and migration 27 adds `cancelled` to the package and Power Platform refresh-job status constraints for owned Viewer read-job cancellation. Migration 27 does not alter session or capability-cache tables. Later migrations add retained report history and private saved-data synchronization. Migration 31 adds atomic, tenant/principal-scoped cleanup for explicitly admitted clean-resync runs, with publication fences and no direct runtime DELETE grants. Migrations 32-33 add the private canonical agent registry and Power Platform queried-type metadata for inventory coverage verification. Migration 34 adds tenant/report-set-scoped reviewed usage associations, revision and cleanup triggers, and association audit actions. Migration 35 adds saved agent-people data. Migration 36 updates only clean-resync source admission to accept automatic-only runs and preserve legacy runs, without widening deletion permissions. Migration 37 resets only Users-sync caches and enforces the current Copilot service-snapshot format; it adds no runtime DELETE privileges. Migration 38 preserves paired access-canary qualification evidence by distinguishing its original and restoration stages. Migration 39 extends the package-refresh default deadline to four hours. Migration 40 repairs migration 19's retained activity payloads by restoring projection version 2 and removing superseded actor aliases; current version-3 payloads and query versions are unchanged. The two-role session, cache authorization, no-alias, and fencing behavior is enforced separately by application code. Advisory transaction locks serialize migration attempts. Unknown/newer or modified applied migrations fail; upgrades are forward-only and an individual failed migration rolls back. Never edit an applied migration; add a new version. Bootstrap uses ordinary operator role/schema privileges, not a required cloud superuser. The runtime database role cannot create schema, own its objects, elevate roles or directly change/delete/truncate audit events, published inventory snapshots or accepted official usage content. Library auto-DDL is disabled.

All available single, selected bulk and block-all mutation routes require a current server-issued preview with `risk: true`, a confirmation hash, and a durable `Idempotency-Key`, then return **202 durable jobs**. The preview includes operation, exact targets and current/requested state, Microsoft Graph endpoint/maturity, delegated permission, actor, affected principal count and rollback limits. Same-key/same-confirmation retries return the original job even after saved package state changes; another payload returns 409. Access and block/unblock operations need no prior canary or additional configuration. Reassignment has no implemented product workflow. Job states are `queued`, `running`, `waiting_authorization`, `succeeded`, `failed`, `cancelled` and `partial`, with no `completed` alias. Items also distinguish `skipped` and `inconclusive`.

- At most two in-process workers, five unfinished jobs per principal and 5,000 items per job. No recurring provider refresh or startup collection.
- Database-time leases last 120 seconds with owner/version fences; up to ten claims, a 30-minute dispatch deadline and seven-day retention. Stale workers cannot commit outcomes or dispatch another item.
- Intent/attempt audit is persisted before remote dispatch. A per-tenant/package advisory lock serializes local operations; under that lock the worker rereads the exact target and compares the frozen mutation-state hash. It then rechecks role/capability and reacquires the exact delegated tenant/account/resource authorization. Writes dispatch once and are never automatically retried. Successful outcomes require bounded provider readback; uncertain accepted writes remain `inconclusive`. `POST /api/agents/bulk-jobs/:id/reconcile` requires current `AgentControl.Admin` plus delegated `CopilotPackages.Read.All`, revalidates around each result, honors cancellation, performs provider reads only and never requires a still-qualified write capability.
- Package mutation-state hashes use fixed field order and canonical principal identities/order, independent of JSONB object-key ordering. Existing captured-state hashes remain unchanged, so read-only reconciliation compares stored and observed access state without treating serialization order as an external change.
- Verified changes, verified no-op outcomes, and authorized reconciliation store the already-obtained exact package readback in the same transaction as the fenced job outcome and audit receipt. This advances the saved inventory revision without another provider request or a fabricated refresh job. The UI reloads saved inventory so membership, counts, sorting and exports reflect that observation. An intervening confirmed clear/resync fences an older in-flight observation; explicit read-only reconciliation can obtain and publish a fresh observation afterward.
- Restart cannot recover MSAL tokens. Unsent delegated work waits for current authentication and explicit resume; completed/uncertain items never replay. Cancel stops unsent items, not an already accepted remote operation.
- Poll `GET /api/agents/bulk-jobs/:id`; cancel with `POST .../:id/cancel`; resume unsent work with `POST .../:id/resume` and `{ "confirmed": true }`; reconcile inconclusive items with `POST .../:id/reconcile`. Tenant/principal filtering applies before job, session and audit access.
- Sessions expire after eight hours, IDs regenerate at login, and only allowlisted account/user state plus a random authentication-transaction handle is serialized. OAuth state, nonce, PKCE verifier, tokens, and MSAL cache blobs never enter PostgreSQL. One-time process-local authentication transactions expire after ten minutes.
- Administrative audit appends confirmed request, attempt start and outcome/reconciliation rows and reads a projection. Unknown legacy tenant attribution is not exposed by scoped app routes.

Requests cap JSON at 512 KiB; package pages cap at 100/5,000 total rows and 2 MB per response; package readiness, inventory-page and detail reads each have a thirty-second provider budget. Other provider requests, including package mutations, retain ten-second limits. Readiness separately bounds token acquisition to ten seconds. Successful package response bodies share the read deadline, and inventory jobs retain their overall execution deadline. Ordinary read retries cap at three with fallback delays capped at 30 seconds; confirmed inventory throttling allows six attempts with 30/60/120-second backoff. Valid provider `Retry-After` values up to five minutes are honored without shortening them; longer cooldowns fail the read rather than retry early. Mutations never retry. Directory search returns at most 50 principals, resolves at most 500 native Entra UUIDs with concurrency eight, rejects duplicate/deleted/unresolved identities and rejects a Graph response whose ID differs from the exact requested ID. Unknown package fields are omitted with value-free schema diagnostics. Package responses are not archived; Power Platform snapshots contain only their validated allowlisted projection.

Package observations reject malformed or oversized facets, access-status strings, version markers and facet collections rather than shortening them or silently dropping entries. Accepted values remain exact; only display names and descriptions may be shortened, without splitting Unicode characters. NUL and unpaired Unicode surrogates are rejected before text/JSONB publication. Creation and modification timestamps must be valid, timezone-qualified ISO 8601 instants; their precision and offsets are preserved, while missing, null or empty timestamps remain unknown. Invalid observations fail with `provider_schema`, before inventory publication or mutation readback can accept incomplete state. Unified observation metadata preserves opaque native IDs as own JSON keys, including names shared with JavaScript object properties.

Package refresh retries with the same idempotency key return the retained matching job; a mismatched request remains a conflict. If a matched job has expired, or the job is cleared between submission and loading its response, submission returns `409 package_refresh_expired` rather than an empty success. Start a new refresh with a new idempotency key.

Package detail reads and access-update prestates must match the exact requested package identity. Access helpers reject missing selected assignments and blank principal identities rather than treating them as empty or silently dropping them; additive all-user no-ops remain unchanged. An unknown unselected scope blocks dispatch, and access readback cannot verify omitted collections or an unknown unselected scope. Access-update preflight reads share the mutation's cancellation signal and correlation ID, and the full payload is validated before the dispatch hook runs.

Package list/detail reads use Graph v1.0 and save only allowlisted complete observations for thirty days; refresh jobs are retained for seven days. Failed or partial refreshes never replace the last complete broad snapshot. Opening Agents with no saved broad snapshot starts one delegated read-only refresh per authorized session; other navigation reads saved data only. The Permissions first-page catalog check does not import inventory. **Refresh agents** explicitly submits and polls subsequent refreshes before reloading saved rows, including retries after a failed initial refresh. Provider-verified management readback publishes an exact saved observation while preserving the broad catalog snapshot and unrelated packages. Preview access and block/unblock use Graph beta and delegated `CopilotPackages.ReadWrite.All`; application permission is not supported. Microsoft documents global cloud and a Microsoft Agent 365 license, but no additional human Entra administrator role. Local serialization and immediate prestate hashing detect observed conflicts but cannot prevent an external administrator's change after the final read. In particular, the full access payload has no documented ETag/`If-Match` or equivalent lost-update protection and can overwrite a concurrent external change. Owner reassignment has no implemented product workflow or documented owner readback. [docs/mutation-canaries.md](docs/mutation-canaries.md) defines optional principal-separated qualification and restoration; evidence is recorded only after an approved cycle is restored and verified.

The initial Agents page reads saved inventory. First-use collection is started through Data sync so its work and upload requirements are visible in one durable run, rather than racing an untracked automatic package refresh. Existing or failed work requires explicit Refresh or resume. The agent modal's inline Manage editor labels its starting values as saved settings and refreshes the exact package when Apply is requested, before presenting confirmation. Opening a standalone single-agent access editor still refreshes the exact package before editing. Bulk access preparation refreshes each selected target before requesting confirmation. These preparation reads do not change provider settings; a failed read never falls back to a mutation preview based only on saved data.

Implemented package access, block/unblock and quarantine operations are on demand in every deployment. An Admin can preview and confirm them without a prior canary, qualification record, or extra mode/configuration. Current sign-in, Admin role, Microsoft authorization, same-origin/CSRF, exact targets, confirmation, immediate prestate checks, audit, one-shot dispatch and provider readback still apply. Optional canaries retain their own approval and restoration rules and never gate ordinary writes. Optional application/shared modes retain their separate configuration and scope requirements.

Power Platform inventory uses delegated `ResourceQuery.Resources.Read` against the global `api.powerplatform.com` Resource Query endpoint. Both Data sync and explicit source refresh request only `microsoft.copilotstudio/agents` and `microsoft.powerplatform/environments`. Embedded agent connector operations and environment type/group/managed metadata are retained as context; they are not separate catalogs or inferred agent relationships. Each explicit refresh uses code-owned structured clauses, `Top=100`, continuation tokens, a 50-page/5,000-row ceiling, 10-second requests, three read attempts, a 10-second retry ceiling and 2 MB response limit. Results are allowlisted and publish only after complete enumeration; raw provider responses, connection/sharing secrets and tokens are discarded. Failed or interrupted work preserves the prior snapshot. Restart converts running jobs to `waiting_authorization` without calling a provider; only an explicit current-user resume can reacquire authorization.

Power Platform projections reject NUL and unpaired Unicode surrogates in required identities or supplied locations before publication; malformed optional text is omitted, and bounded locations never split a Unicode character. An entirely malformed channel list remains unknown, distinct from an explicitly supplied empty list. Optional timestamps require a valid, timezone-qualified ISO 8601 instant and retain the existing UTC millisecond normalization. Malformed dates remain unknown rather than rolling into another calendar day or establishing a published lifecycle. Connector/capability status comes only from fields documented for that resource type; unsupported environment fields cannot create agent capability metadata.

The Power Platform capability check samples at most one environment row and never follows continuation tokens or saves inventory. A valid provider total above the refresh ceiling does not invalidate this bounded access check. Its ten-second overall deadline remains enforced alongside caller cancellation; a cancelled or expired check cannot report success.

Inventory snapshots are tenant/principal-private. Viewer and Admin can filter, sort, page, inspect and export authorized agents even when live provider access is unavailable. There is no generic resource browser, snapshot-picker API or non-agent export. Full Microsoft provider roles are Global Administrator, Power Platform Administrator, Dynamics 365 Administrator and Global Reader; AI Administrator/AI Reader support AI-scoped resources. Optional ID-token `wids` claims remain diagnostic hints, not proof of collection success or permission grants; all request plans use the same two-type supported universe. Explicit narrower query scopes remain distinguishable from complete collection, and unrequested or unauthorized data is never a verified zero. Snapshot resources expire after 30 days and refresh jobs after seven days through operator retention. The app supports global cloud only; sovereign-cloud endpoint/support differences are reported as unsupported configuration rather than guessed.

A completely enumerated refresh replaces the same saved scope even when previously observed identities disappear or the count decreases. The query client binds its result to the actual queried resource types and environment. Publication requires that scope to agree with the authorized request, all pages to complete, provider and collected counts to agree, and normalized source identities to be unique. Failed, malformed, interrupted, or scope-mismatched enumeration preserves the previous snapshot.

Saved inventory checks run automatically; no manual verification or administrator approval is required after sync. Agents keeps diagnostics out of the management list, showing only a compact notice if inventory needs attention. **Sync > Inventory health > View diagnostics** opens the detailed receipt and optional **Verify saved inventory** action, which reloads saved data without starting provider sync or clearing records. Power Platform readers compare actual saved rows and normalized identities with the captured provider total, collected count, queried types, and environment. Graph unified reads verify broad and exact snapshot counts so missing rows cannot masquerade as intentional package removals. Every unified response includes a full-inventory verification receipt: source target counts, unique represented memberships, logical agent count, and source-scope/identity checks, computed before filtering and paging. Pending or invalid metadata and ambiguous/conflicting links require attention; a missing optional role claim does not make a verified collection partial. Failed verification is an explicit error, not a successful empty result.

Verification covers the authorized saved queries, not every possible agent surface or a new live Microsoft read. **All environments requested** describes the absence of an environment filter, not a fabricated directory-role attestation. Microsoft inventory excludes classic/V1 bots and can lag source changes, typically by about 20 minutes. Source observation times and saved-data verification times remain distinct. See [verified inventory operations](docs/deployment-setup.md#verified-power-platform-inventory). Migration 33 replaces role-derived coverage JSON with persisted actual `queried_types`; it preserves roles, source data, counts, timestamps, and canonical identities. A queried type with zero returned rows is a verified query result; an unqueried type remains `not_requested` or explicitly scope-filtered.

Verified block/unblock and access changes update saved control state without replacing inventory identity evidence or requiring a full sync. Migration 44 separates these observations, protects newer control state from late refreshes, and repairs audit-proven legacy post-action splits on the next saved Agents read when valid identity evidence remains. Deploy the migration and runtime together; see [post-action inventory repair](docs/operations.md) for revalidation and retention rules.

Newly supplied native identity fields, package revision markers or element types in a control readback require identity revalidation rather than being discarded while an old link stays active. Newly declared or newly multiple declarative agents also require revalidation. A changed or malformed bot identity also invalidates the old association when the readback supplies only `Bots` or only `CustomEngineCopilots`. Omitted/empty optional groups and case-equivalent identities still preserve saved evidence; control readbacks never replace that evidence or qualify a new native link. A control-only record without saved inventory identity keeps its verified control state but has missing identity details until a separate identity refresh.

Inventory admits at most four active refreshes globally and five unfinished requests per principal. Queries have a 120-second overall deadline, active execution a 150-second bound, and unsent requests a 30-minute dispatch window. Saved scope selection and recent job discovery survive navigation/restart without submitting a scan. Explicit resume revalidates the current principal; logout cancels inventory work without waiting under the account-session lock. Publication rechecks authorization, refuses stale/superseded work, and preserves broad scopes when a narrow scope completes. Changes to optional role hints do not interrupt an unchanged query scope; a real type-scope change requires a new refresh instead of an irrelevant reauthorization loop. Source freshness remains readable after its refresh job expires. Sync history and Inventory health diagnostics open the exact Power Platform job in **Sync** at `/sync?powerPlatformJob=<id>`, including older failed, waiting, running and completed jobs. Inspecting it reads only saved diagnostics. Resume and cancel target that exact source job; recovery from a failed or cancelled job explicitly creates a new refresh with the original scope. An unavailable job is not replaced by the latest job.

The agent-centered Power Platform schema is a fresh-initialization contract: jobs, snapshots and resource rows accept only the two supported types. No obsolete catalog-data conversion or compatibility backfill is provided.

Exact identifier outcomes are computed server-side before paging. Resource type, identifier kind, tenant and required environment remain distinct; ambiguous candidate details are bounded to 20 identities with their total retained. The unified agent view groups source-declared associations for presentation without merging the underlying saved resources or replacing native mutation targets. Saved Purview/Defender identity links use verified current inventory for the same Viewer/principal, including when optional role claims are absent; they do not grant live provider access or expose another user's inventory. CSV exports apply the same Viewer/principal-private scope and neutralize spreadsheet formula prefixes. Unified CSV includes the full-inventory verification status, scope, check time, source/unique/logical counts, and checks alongside the inventory revision.

### Agent identity links

The unified inventory includes every authorized saved Graph package and every saved Power Platform `microsoft.copilotstudio/agents` resource. Agent flows are distinct provider resources and are not collected by this two-type agent/environment source; an invoked-flow relationship cannot be inferred from inventory membership. Graph-only and Power-Platform-only agents remain visible; matching does not require both providers to be available. Source coverage, freshness and errors remain separate.

Package detail can contain an `AgentMetadatas` element whose JSON definition reports `SourceIds.EnvironmentId`, `SourceIds.CdsBotId`, `SourceIds.SchemaName` and `AgentIdentityId`. The matcher requires the same tenant and exact environment. It compares explicit CDS-bot or Entra-agent identities with corresponding typed inventory identifiers. When typed bot fields are omitted, it also accepts the corroborated combination of the same environment, exact schema name and inventory native GUID equal to the source-declared CDS bot ID. A name or GUID alone is never enough. Conflicting fields, disagreements between package representations (including schema names), multiple candidate resources, malformed metadata and cross-environment matches remain unlinked. Schema names are compared case-insensitively and may be absent for typed-ID links, but a supplied malformed schema name in either source is not treated as absent.

Schema disagreements for the same declared environment/CDS identity remain conflicts even if only one representation matches inventory, and cannot qualify a control ID. Partial metadata containing only an environment or schema name still constrains declarative-manifest and custom-engine associations; it is not an identity proof by itself. Source-only declarative packages with distinct declared environments remain separate even when their manifest IDs agree.

Custom-engine association checks every independently matched resource, including Entra-agent and Entra-application matches, before attaching an otherwise unlinked package. When a shared bot application spans distinct matched resources, unproven aliases remain ambiguous while direct links stay intact. A CDS/native anchor is still required to extend a link; secondary identity matches alone do not become anchors or control-ID proof. Packages whose matching details are missing, expired, invalidated or awaiting identity revalidation cannot acquire links or source-only grouping through a shared bot application.

This inner metadata schema was observed in provider responses; it is **not a publicly documented package-to-Power-Platform identity contract**. Evidence is marked `source_declared_metadata` and retains element IDs and field paths alongside source observation metadata. Matching names, equal manifest/native GUIDs, shared blueprint IDs and associated application registrations are not sufficient to consolidate agents. Linking never grants permission.

Retained detail metadata is reused across an older-style broad summary only when a valid unchanged provider modification time and unchanged identity/version markers establish the same package revision. Positive catalog identity evidence, including native metadata, element types and declarative ambiguity, must also agree with the retained details; matching revision markers do not hide contradictory evidence. Access memberships explicitly supplied by a newer catalog read, including empty lists, take precedence over older detail enrichment; newer detail reads and enrichment of omitted membership remain supported. A completed identity collection or newer exact observation that omits metadata does not resurrect an older link. Source-qualified detail links resolve to the combined agent independently of the current page, preserving environment identity even when native IDs repeat.

The checked-package count measures completed detail collection, not successful identity matches. The count and matching explanation use the same collection evidence, including legacy exact observations and retained details. When a collected package has no `AgentMetadatas`, its matching explanation reports missing provider metadata rather than directing the user to repeat already completed collection. Sync also exposes conflicting and ambiguous identity counts; source-only records are not, by themselves, evidence of missing inventory.

Bulk-operation reference searches filter unified rows before pagination using the current tenant and principal's package audit targets. The lookup reuses the inventory transaction's database connection rather than acquiring another connection while holding the snapshot. A linked row is included when any of its packages matches; references do not reveal another user's operations or turn Power Platform resource IDs into package control targets.

Every full agent refresh enumerates the catalog and then collects exact details for every package with four continuously replenished workers, within a **four-hour execution ceiling** and the existing 5,000-package/100-list-page limits. The same execution ceiling covers selected-detail refreshes (1-100 targets) and single-package refreshes; the database deadline starts afresh when the job is admitted. Migration 39 updates the dispatch default without resetting saved data. A slow or retrying detail does not hold up the other workers. Sync shows completed identity checks, not packages listed: the current implementation issues 1,071 detail requests for a catalog of 1,071 packages, even if the list already includes detail fields. Whether those additional reads supply information is measured by [job-scoped package sync diagnostics](docs/operations.md#graph-package-sync-diagnostics); it is not assumed from the API's inconsistent list/detail documentation. Progress writes are serialized and normally grouped every four completions. Package read observers no longer give up after five or sixteen minutes; cancellation, changed account/request ownership, unmount and terminal status still stop observation. Cancellation or a terminal failure stops new reads, aborts in-flight requests and drains the workers before ending the job. Authorization revalidation and atomic publication cover the entire collection; failure retains the previous complete snapshot, and an exact 404 records absence.

Package refresh capacity counts each pending or running authorization/collection once, up to four foreground jobs and two independent automatic-detail jobs. Admission reserves the lane from the persisted job mode before contacting Microsoft, including explicit resumes; pending job lookups are bounded by the combined six-job capacity. The five-job per-principal admission limit counts only unfinished jobs still within their dispatch and retention deadlines; retained expired jobs do not block a fresh refresh. Permission-denied startup is saved as a failed job with permission guidance, not a request to sign in again. Cancellation and sign-out also stop jobs still acquiring authorization, and interrupted admission does not become a permission failure if a late provider denial arrives. Startup readiness checks and token acquisition run outside the account-session lock so they cannot block sign-out; final admission rechecks the session generation under that lock before marking the job running. Shutdown rejects new starts and drains pending starts as well as active collection before closing persistence.

Package reads retry transient HTTP 500/502/503/504, connection/body transport failures and individual thirty-second read timeouts, at most three failures with bounded backoff. These per-request limits protect against stuck requests; they are separate from the four-hour job ceiling. Healthy inventory reads initially have no artificial start-rate delay. HTTP 429 and HTTP 424 responses explicitly reporting "too many requests" trigger a shared cooldown and adaptive pacing: 250 milliseconds initially, doubling after further throttled request generations up to two seconds. Concurrent failures from the same in-flight generation apply only one rate penalty. A minute of successful, throttle-free reads permits a gradual rate increase, rather than keeping a permanent four-per-second cap. Provider `Retry-After` takes precedence; inventory jobs can honor waits up to their four-hour ceiling and retry throttling until cancellation/deadline instead of abandoning collection after six throttle responses. Other callers retain bounded retry budgets; writes never retry automatically. Inventory reads reacquire the delegated/application token through the existing token cache before request admission, so a long job is not pinned to its initial bearer token. Tokens aged by a long queue or cooldown are renewed without losing the read's queue position; admission rechecks cooldowns afterward and preserves spacing, so concurrent refreshes do not starve or burst. Cancellation and the overall deadline interrupt waits and token renewal; malformed/oversized responses and genuine authorization failures remain terminal.

After collection, transient readiness timeouts/network failures/throttling are retried against current evidence **without downloading the packages again**. The complete result remains in memory while Sync reports the readiness wait. Each publication attempt revalidates the principal, role, applicable application scope and capability; actual denials, cancellation, sign-out, configuration changes, supersession and database publication failures are never turned into success. Slow provider checks and retry waits do not hold the account mutation lock. No snapshot is published before authorization succeeds, and a process restart still requires a new authorized collection. Cross-run whole-detail caching is not inferred from identity revision markers: those markers do not prove unchanged access memberships. Terminal failures retain sanitized diagnostics in Sync and Docker logs. Do not reset the database to fix a provider or readiness failure.

For existing saved inventories without collected identities, opening Agents with current delegated read authorization starts one durable, idempotent identity collection per source snapshot, or follows an already-running broad refresh. It continues across tabs without opening a modal. Failed/cancelled collection is not automatically restarted; retry deliberately from Sync. Catalog GET/filter requests themselves remain saved-data-only.

The catalog has one row and one selection checkbox per verified agent, including all of its published package versions. **Manage** opens access, installation/block and quarantine controls together. Overview presents administrative information; source/link diagnostics remain under technical details and can optionally be enabled as table columns.

Package block/access and Copilot Studio quarantine remain distinct actions with separate state, permissions, confirmation and readback. Native targets are preserved. Quarantine requires a fresh inventory environment/CDS-bot identity; if its typed bot field is missing, the server can qualify the explicit Graph CDS bot ID only using the corroborated environment/schema/native-ID match and same-principal, current identity evidence no older than 24 hours. The catalog and target picker use the same proof as server preview/submission. Neither a frontend inference nor a generic "Disable" action substitutes for those checks.

## Copilot Studio Quarantine

Quarantine is delegated-only and global-cloud-only. It uses Power Platform audience `8578e004-a5c6-46e7-913e-12f58912df43` and scope `CopilotStudio.AdminActions.Invoke`. Viewer may observe authorized exact status; changes require `AgentControl.Admin`, provider-issued delegated authorization, approved consent, and explicit confirmation. No prior mutation qualification is required. Agent Control does not reconstruct quarantine eligibility from optional `wids` claims or hard-deny solely because such a claim is absent; the provider remains authoritative and may deny the request. Application credentials, package IDs and display names are not substitutes. Classic/V1 bots remain unsupported.

The implemented endpoint contract is `GET .../copilotstudio/environments/{EnvironmentId}/bots/{BotId}/api/botQuarantine?api-version=1`, with one-shot POSTs to `SetAsQuarantined` or `SetAsUnquarantined` using the same `api-version=1`. Microsoft documentation rechecked on 2026-09-10 is inconsistent: the Copilot Studio quarantine guide specifies `1`, while all three generated REST request examples specify `2024-10-01`. Agent Control follows the Phase 09 contract and guide with version `1`; it never retries against another version. An approved exact-target live probe must qualify that version before any live canary. Resource Query inventory separately remains `api-version=2024-10-01`.

Controls accept only a current principal-private `microsoft.copilotstudio/agents` snapshot and its exact native resource, environment and CDS bot IDs. Inventory older than 24 hours, expired/removed/ambiguous targets and absent IDs disable status and mutations. An explicit status read retains `isBotQuarantined`, exact `lastUpdateTimeUtc`, observation time and correlation for 30 days with a 60-second cache. It stays visibly separate from lagging inventory state; unknown/unavailable never becomes `false`, and direct state never rewrites the inventory snapshot.

Status, preview and submission retain their initiating account-session generation across inventory/cache lookups, provider reads, observation publication and job dispatch. Logout or a superseding sign-in stops further work, including cache-only results and a newly persisted job's launch. Idempotent receipt lookup treats snapshot UUID letter case as equivalent while preserving exact native-resource IDs, action and confirmation hash.

Provider requests have a 10-second deadline, and each GET operation bounds retries and retry waits to 30 seconds. Rejected-response cleanup never blocks those deadlines. Cancellation is checked before dispatch, after response-body consumption and before reporting GET convergence; an expired deadline is reported as `provider_timeout`, not a successful observation.

Single and bulk operations are bounded to 25 targets. Preview freezes direct prestate/timestamp, exact targets, actor, capability revisions and requested state. A normal submit requires current Admin/provider authority and confirmation, not canary evidence. Workers serialize each provider target, perform two current pre-reads, mark the one permitted POST sent durably, and require bounded GET convergence before success. The provider documents no conditional-write header, so timestamps cannot prevent a concurrent external change after the last read. Accepted, timed-out or interrupted sent work becomes `inconclusive`; reconciliation performs GET only and never replays or automatically inverts a partial bulk result. Startup moves unclaimed/unsent work to `waiting_authorization` without a provider call; explicit resume reacquires current delegated authorization. Viewer and Admin can review current-principal quarantine audit events; Admin does not gain another principal's private audit or job data.

Makers may still see and test a quarantined bot in Copilot Studio while users cannot use it through connected channels. Graph package blocking is an independent control with independent state and optional qualification evidence. [docs/mutation-canaries.md](docs/mutation-canaries.md) defines the separate optional quarantine canary procedure. The recorded phase environment reported `authConfigured: false`; no exact live target or canary approval was available, so that phase's live read/write evidence is `unavailable`, not passed from fixtures.

## Purview Audit Search

## Legacy Audit Import

[backend/scripts/import-legacy-audit.ts](backend/scripts/import-legacy-audit.ts) is an **operator-only** SQLite reader, excluded from the runtime image and ZIP. Never point it at a live SQLite/WAL file. Obtain a SQLite online-backup/safely closed standalone backup and its independently recorded SHA-256, then mount it read-only into an operator container. Phase 12 owns actual production backup/import execution; this phase tests fixtures only.

```bash
docker run --rm --network agent-control_default \
  --mount "type=bind,source=$PWD/.local/agent-control/secrets,target=/run/secrets,readonly" \
  --mount "type=bind,source=<absolute-protected-backup-directory>,target=/legacy,readonly" \
  -e PGHOST=postgres -e PGUSER=agentcontrol_admin -e PGDATABASE=agentcontrol \
  -e PGPASSWORD_FILE=/run/secrets/postgres-admin \
  agent-control-operator:local backend/scripts/import-legacy-audit.ts \
  /legacy/audit-backup.sqlite <expected-sha256>
```

The importer validates the known schema, a 64 MiB/100,000-row limit, integrity and allowlisted audit fields. It assigns deterministic source IDs and atomically verifies exact row count/content hashes plus a checksum-keyed receipt. Same-backup retries are idempotent; changed, malformed or unapproved fields stop the entire import for operator review. Never edit the source backup to make a check pass. Unknown tenant remains unknown and restricted. Old in-memory jobs/sessions were never in SQLite: require login and manually reconcile legacy writes without replay.

## Official Usage Reports

The only official per-agent and per-user usage authority is the Microsoft 365 admin-center **Copilot Agents usage** report. Microsoft currently documents 7- and 30-day report windows and says usage can appear within one hour of interaction; treat that as source latency, not a guarantee that an operator has imported the latest export. Microsoft Graph `copilotReportRoot` has three current `v1.0`/`beta` methods for licensed Microsoft 365 Copilot app user counts, trends and user activity, but none returns the equivalent per-agent Agents, Users & agents and Users datasets. Import therefore remains a manual operator workflow. Audit, Defender, telemetry, transcripts and package events are never substituted or relabelled as official usage.

1. In the Microsoft 365 admin center, open **Reports** (use **Show all** if Reports is hidden), then **Usage**. Under **Reports**, select **Microsoft Copilot > Agents**.
2. Select the same documented 7- or 30-day period for the complete bundle. Select each **Agents**, **Users & agents**, and **Users** table/tab and use its **Export CSV** action. Keep the original CSV files until the import is accepted.
3. In Agent Control, sign in with `AgentControl.Admin` and open **Sync > Import reports** (`/sync?reports=import`). Automatic initial setup does not wait for manual reports; retained legacy runs can still offer an upload step. The UI does not require manually entered dates.
4. Choose all three CSVs, review the server-produced kind, hashes, schemas, row counts, period, source basis, warnings, reconciliation and complete bundle hash, then accept the reviewed bundle. All three kinds publish in one revision-fenced transaction. Missing companion files remain resumable actor-owned staging or an incomplete retained set and never replace active data.

The parser accepts only the current Microsoft-documented and fixture-observed headers listed in [the official usage import runbook](docs/official-usage-import.md), validates UTF-8/content/row/field/byte bounds, and rejects unknown required-column changes as schema drift. Filenames, MIME types and extensions are not reporting-period authority. The supported CSVs contain no report-period or source-as-of metadata columns. Available last-activity dates are retained as `activity_range`, not a proven reporting window; reports without activity dates have unknown coverage. Explicit API-supplied periods remain `operator_asserted`. Source freshness is not inferred from upload time or activity dates.

Accepted observations are immutable and retained across imports. Independent complete bundles add to history; they do not delete older reports. Semantic duplicate detection ignores row ordering and CSV formatting, reuses unchanged observation payloads, and preserves report associations. Reuploading the same content does not refresh its acceptance time or change the active selection. Changed content creates a new selected report set even for the same known reporting window; no correction checkbox is required. The importer rejects duplicate report types within a draft rather than silently replacing an earlier file. An Admin's choice in the **Report set** dropdown on Agents or Users immediately switches the shared tenant-wide reporting selection; exact history inspection remains read-only. Dates are labeled as observed activity unless an explicit reporting window is known. Deleting the active set clears selection without falling back to an older set. Original upload bytes are never archived.

Viewer and Admin can browse the single paginated history table in **Sync > Manage reports** (`/sync?reports=manage`) and read an exact historical report set in its snapshot inspector (`/sync?reports=snapshot&snapshot=ID`) without changing the current selection. Admin retains confirmed import, selection, and deletion actions; Viewers have read-only report access. Agent CSVs are exported from the snapshot inspector; user CSVs from **Users > Reported activity**. Downloads use the exact displayed report set and applied filters, not only the visible page, so a concurrent active-selection change cannot silently switch the data. User filters select people; their CSV retains all relationships of matching users, with independent user totals repeated rather than summed. Pending or failed reads disable export. Changing filters, leaving the view, or changing account/authorization cancels pending exports; late responses cannot start a private download after that boundary. History can extend beyond Microsoft's rolling 7/30-day export window, but those CSVs are aggregate snapshots, not event logs. Overlapping totals are never added into an invented all-time total, and inferred activity ranges never become proven reporting coverage.

Old `/official-usage` bookmarks migrate automatically. A valid `staging=ID` takes priority and opens `/sync?reports=import&staging=ID`. Otherwise, `view=history` opens `/sync?reports=manage` even when `snapshot=ID` or `window=N` is present. Without `view=history`, snapshot selectors or valid `window=N` links open `/sync?reports=snapshot`, retaining bounded `snapshot`/`window` values; the remaining default/overview links open Manage reports. New accepted-job **View snapshot** links instead emit `/sync?reports=snapshot&snapshot=ID` directly; jobs without a retained snapshot open Manage reports. The inspector can also open the current snapshot without an explicit ID. This consolidation deletes no source data and changes no `/api/official-usage` data APIs, import services, authorization, storage, or retention behavior. See the [workflow rationale and bookmark contract](docs/official-usage-import.md#one-home-for-each-workflow).

Viewer and Admin can read and export aggregate and user-level accepted official usage. Only Admin can stage, review, accept, select, and delete operational report sets or confirm legacy report-to-inventory associations. A full report Agent ID can automatically attribute usage to an exact authorized current Graph package and its existing logical agent; it never becomes a native management credential or an arbitrary cross-source identifier. Names and creator strings are never identity keys. An explicit administrator-reviewed association remains a report-set-scoped override, separate from automatic matching and provider verification, and only projects metrics for its exact authorized source target. Pseudonymous usernames remain case-distinct and explicitly scoped to their report set and Users/Users & agents versions. Licensed and unlicensed active-user categories are not additive even within one agent because license changes can place one person in both categories; their sum is never presented as a distinct-user total. Exact distinct active-user totals include only positive-response identities in the case-sensitive Users plus Users & agents dataset union, while each source's response total remains independent. Missing per-agent identity evidence stays unknown; explicit zero-response rows yield zero active users and remain visible in reported relationship counts. In Users & agents, last activity is the date the agent was last used by anyone, not that user's last interaction. User recency comes only from Users and is unknown when that row is absent. Source disagreements remain visible instead of being corrected or hidden.

Staging rows expire after 30 minutes and startup plus periodic runtime cleanup removes abandoned preview rows. Accepted content is retained until explicit deletion; payloads shared by another retained report survive deletion of one report. Content-free operation receipts expire after 180 days and minimal import audit after 90 days; neither TTL expires accepted history. Upload parsing and processing have an active 15-second wall-clock timeout, and disconnected work keeps its admission slot until parsing/database work has settled. Admission caps are 8 MiB and 50,000 rows per file, two concurrent uploads per process, nine retained staging rows/150,000 rows/96 MiB per actor, and 30 rows/500,000 rows/256 MiB per tenant. Run the internal [operator retention procedure](docs/operations.md#retention) during ordinary maintenance to remove expired work and orphaned payloads after confirmed deletion. `OFFICIAL_USAGE_STALE_AFTER_DAYS` defaults to `35`, accepts 1 through 365, and marks a selected set stale when either report-period age or accepted-set age exceeds the threshold. Staleness does not delete history. `never imported`, `incomplete`, `active`, `stale`, `not selected` and `deleted` remain distinct and never trigger another source fallback.

The legacy browser key `agent-control:usage-reports:v1` is detected by key enumeration only. Its value is never read, parsed or uploaded. Every affected authenticated browser receives a content-free notice regardless of app role; only Admin receives cleanup controls. The key survives sign-out, unmount and failed import. It is removed only after server-acknowledged successful original-file re-import confirmation or explicit discard acknowledgement; unrelated local-storage keys remain untouched. Storage at an older origin such as `http://localhost:5173` cannot be detected from `http://localhost:3001` and must be handled explicitly at that origin.

Operator workflow: [docs/official-usage-import.md](docs/official-usage-import.md). Microsoft source: [Microsoft 365 Copilot Agents usage report](https://learn.microsoft.com/en-us/microsoft-365/admin/activity-reports/microsoft-365-copilot-agents-new?view=o365-worldwide).

## Permissions And Saved Data

Permissions is a setup-and-troubleshooting page: **Issues**, **App prerequisites**, and collapsed **Log collection setup**. It shows the signed-in account's app role and actual recent failures, not access tables, readiness counters or warnings about unused features. A healthy view says **No issues reported.** This is a report of observed failures, not a claim that every operation has been tested.

While **Check status** runs, a temporary panel names the active checks and shows the server-reported number reviewed. Loading saved results is separate from checking Microsoft access; reviewed does not mean access was granted. Animated indicators respect reduced-motion settings, and progress reads stop when the panel closes.

**Required API permissions** expands a deduplicated permission-to-feature reference. Each grant names the exact app area/action that uses it; OpenID Connect scopes, delegated permissions and collapsed optional application permissions stay separate. The reference identifies unused `User.Read` and explains why separately requested narrower read scopes must remain. Grant changes and tenant admin consent happen outside the app. Log setup holds the Microsoft 365 connector, Copilot Studio activity and definitive Purview auditing checks. **Details** on a failed feature shows required setup and links, with diagnostic fields under **Technical details**.

Every signed-in account can open **Permissions**, including an account awaiting internal role assignment. Registered adapters include package delegated/application reads, on-demand Admin-confirmed package access and block/unblock, directory lookup, delegated Power Platform inventory, delegated Copilot Studio quarantine status and on-demand Admin-confirmed changes, delegated/application Purview Audit Search, Defender hunting and local official report import. Delegated Purview and Defender operations establish principal evidence through the explicit bounded request; application/shared mode keeps its separate Admin approval and qualification. Owner reassignment has no implemented product workflow or documented owner readback; contract definitions alone do not advertise working integrations.

Permission rows consume the backend's exact resource audience, token mode, permissions, Microsoft/internal roles, licenses, cloud, configuration, source links, safe evidence and freshness. A decision reports capability ID, status, authorization, freshness, optional `token`, `provider`, `local`, `on_demand`, or `qualification` verification, timestamps where applicable, preview-qualification state, sanitized evidence, and remediation. `on_demand` permits a role-authorized user to request an implemented operation; reads do not require change confirmation, while Admin writes require choosing and confirming exact targets. Provider tokens/permissions are checked when the request runs. It is not token acquisition, live operation proof or a qualification claim, and requires no evidence-expiry timestamp or prior canary. Failed, unchecked, disabled and expired provider checks carry no successful verification claim; the UI also guards older payloads that advertised only a probe type. Safe diagnostics may include HTTP status, bounded provider error code and correlation ID, never raw responses or tokens. `qualification` denotes separately recorded optional evidence, never an ordinary-write prerequisite or an automatic canary. A capability view may include top-level `enabled`; the backend currently emits it for every view, but consumers tolerate omission. It drives application enabled/disabled presentation, with `configuration.enabled` retained as a compatibility fallback. `enabled` is `false` only for a disabled application capability, while delegated and local capabilities are enabled. Application definitions may also report shared-data-scope configuration. After an assigned user authenticates, the UI loads the catalog and runs one bounded session-scoped delegated check when visible. Further checks require **Check status**; expiry and tab focus only age local diagnostics. One check promise is allowed per tenant/principal/sorted-role session generation; requests carry abort signals, and logout, unmount, or tenant/principal/role changes abort and fence stale results.

The header shows **Permissions**, an actual issue count, or a failed-check notice. Unchecked, successful, stale, disabled and role-inapplicable capabilities are not issue rows. Recent `operationFailure` metadata can report a real license, report, identity or control failure without changing its main authorization decision or fabricating provider verification. The next successful operation clears that report; expiry removes it from the page. Opening Permissions displays already-loaded diagnostics without another check. **Check status** refreshes those diagnostics; it never repeats a license sync, hunt, import or mutation. Issue details close when updated diagnostics show the failure resolved, expired or outside the current session scope.

Automatic-check setup and retry guidance applies only to capabilities included in the bounded delegated check. Shared application access requires an explicitly approved application-scope check or operation; **Check status** does not run those checks. License assignment and Copilot usage reads are requested from the dashboard, not by **Check status**. An explicit on-demand read refreshes expired capability evidence through a token-only check before proceeding; fresh failures remain enforced until expiry or an explicit targeted recheck. Their on-demand remediation describes a read without target-selection or change-confirmation instructions. The backend and permission UI share the same automatic-check eligibility rule; this guidance does not broaden authorization or start provider work.

On-demand admission stays an internal authorization contract, not a status the user must interpret. Current Admin authority, exact-target confirmation, provider authorization and readback remain required for implemented writes.

Initial automatic checks wait for a hidden page to become visible, including when no evidence has an expiry yet. Session changes synchronously discard cached decisions so signing out and back in as the same principal cannot reuse the previous UI authorization state. Failed catalog recovery clears any cancelled check's pending indicator, and unmount aborts the active initial check or explicit reload. There are no recurring expiry checks or expiry retries. A transient request failure still receives one abortable transport retry. Local diagnostic-expiry delays are capped at the browser's 32-bit timer limit.

The initial `on_demand` decision is replaced by the initial non-mutating token check for package access/block and quarantine management. Successful scope acquisition reports `verification: token` with expiring account-specific diagnostics, not provider-operation proof. Diagnostic expiry alone does not disable an attempt from a previously available delegated token/provider decision; the server and Microsoft enforce current authorization when the operation is requested. This does not label expired diagnostics as fresh verification or relax application/shared-scope requirements. Known missing grants and interaction failures remain enforced. Background saved-inventory reads likewise leave exact-package actions usable while selection and revision-bound exports wait for the new page. A missing permission links to **Admin setup**, while normal sign-in handles MFA/session renewal. Check status neither grants permissions nor performs a package or quarantine operation.

Within the running capability service, decisions, catalog assembly and explicit Audit/Hunting evidence recording reject account invalidation or application-configuration changes that occur while their asynchronous work is pending. Reads wait for queued evidence/configuration mutations, so a new check cannot reuse evidence that is still being invalidated; if invalidation persistence fails, old evidence remains blocked until a later cleanup succeeds. Provider HTTP 429 responses retain the throttling cooldown even when an adapter reports a generic provider error.

Automatic checks reuse fresh evidence and coalesce equivalent in-flight checks. Catalog/check transport errors retry once after one second for network failures and HTTP 408/500/502/503/504; no warning appears before that attempt completes. Deterministic denials, invalid requests and throttling do not use this retry. Cached transient delegated-check failures are confirmed before appearing on the initial page. Earlier authorization decisions stay unchanged while retrying.

An expiry check that fails transport or returns still-expired evidence additionally receives one delayed retry after 30 seconds per expired-evidence signature. HTTP success alone does not reset that budget. **Check status** reloads the catalog and calls the bounded check with `?retry=failed`, preserving fresh successes and throttling cooldowns. Persistent failure is reported concisely, with stage and sanitized diagnostics in Details, never inferred missing permissions from a network error. Missing grants link to **Admin setup**; actual interaction/expired-authorization errors offer normal **Sign in again**. Neither check status nor a recovery link grants permissions or starts a provider operation.

Ordinary catalog, directory and inventory checks may call their bounded read adapter and are provider-verified only after success. Quarantine read, Purview and Defender readiness acquire only the scoped token and do not prove exact provider-operation or license access. Package access/block and quarantine management are `on_demand`: the authorized Admin chooses a target and confirms; the submitted request validates current provider authorization and exact prestate/readback without prior canary evidence. Management availability itself selects no target, calls no status or mutation, executes/resumes/reconciles no job, and runs no canary; Viewer remains `missing_internal_role`. A successful explicit bounded Purview/Defender operation upgrades that capability evidence to provider verification. API permission grants remain administrator prerequisites. MFA and Conditional Access can still require normal sign-in; interaction-required and expired-authorization check errors remain `unknown` with their exact sanitized evidence category rather than becoming `missing_permission`. Ambiguous authorization and provider failures become `provider_error`; explicit unsupported responses become `unsupported`. Actual missing or expired authorization stops provider work, while authorized saved package observations, saved Power Platform snapshots, saved reports and local audit remain accessible.

**Refresh agents** creates and polls a durable package refresh; **Refresh inventory** creates a Power Platform refresh. Opening Agents without a broad saved snapshot starts one initial delegated read-only refresh per authorized session, with explicit Refresh for retries. This is separate from Permissions checks: those never import inventory, submit writes/canaries, create Audit Search queries or Defender hunts, check application/shared modes, create data-refresh jobs, or run raw-data collectors. Package details show saved observation time/expiry, source, v1.0-read/preview-control maturity, availability, deployment and assignments. Package block is distinct from Copilot Studio quarantine. Access replacement can overwrite an external concurrent change because no conditional-write protection is documented; owner reassignment has no implemented product workflow or documented owner readback.

There is no standalone Jobs dashboard. **Sync** owns collection progress and history, **Manage reports** owns CSV drafts and retained bundles, and entity investigation views own their searches. **Agents > Access and availability** owns package-control progress, cancellation and explicit recovery; **Audit** retains administrative outcomes. A normal sync starts a new run rather than retrying an old run's incomplete sources. Backend job records and authorization boundaries remain unchanged.

Sync history uses recorded start time with explicitly labelled fallbacks for older payloads. Duration requires genuine start and finish times and includes waits; a later update never fabricates completion. Counts remain source-qualified: completed sync sources and observed/saved packages or resources. A full observed count does not turn a failed or incomplete outcome into success. Sync runs and their underlying source jobs are separate, non-additive records.

Sync history consumes `GET /api/workbench/jobs`, an authorized bounded projection of only sync runs and Graph / Power Platform refreshes, not a complete audit archive. It no longer loads package-control, quarantine, CSV staging, Purview or Defender jobs for the retired Tasks dashboard, or returns that dashboard's recovery-action flags. Those jobs and their controls remain in their owning workflows; the Sync history request does not query them. Unavailable collection sources are named without discarding other records; failed reads do not appear as successful empty history. Package-control status polling pauses after five minutes and offers **Refresh status** in the same Agents progress panel. The saved active task is restored after a reload; if sign-in cleared its browser pointer, Agents checks the current principal's latest 50 retained tasks and restores the newest unfinished or uncertain task without dispatching a change. **Resume unprocessed tasks** requires explicit confirmation and never replays sent or uncertain changes.

Viewer may create, resume and cancel their own delegated read jobs, including package and Power Platform refreshes, but not operate imports, provider changes, mutation qualification, configuration, or mutation-job controls. Admin adds those supported administrative controls without widening principal-private caches. Recovery uses the existing action metadata, exact job ID and backend role/capability checks; uncertain-write reconciliation is read-only, and cancellation does not undo already dispatched work.

Purview and Defender search metadata does not prescribe one fixed capability: their forms check the selected authorization mode, and their backend services enforce that mode's current authorization and scope. Qualified application searches do not also require delegated readiness. A null capability in these action entries is not an authorization bypass or permission to fall back between modes.

Permissions keeps optional application grants under **App prerequisites > Required API permissions > Optional application permissions**. Disabled modes are not issues; an enabled mode appears only when it has an actual recent failure. Application mode remains explicitly approved and never becomes an automatic fallback.

Defender hunting needs no separate delegated approve/run qualification ritual. A Viewer or Admin submits one explicit bounded hunt; the actual request establishes provider evidence for that principal and exact tuple. Ordinary delegated jobs have no retained-scope binding and remain tenant/principal-private, including from other Admins. Optional delegated qualification APIs may remain but are not prerequisites. Automatic permission checks acquire only `ThreatHunting.Read.All` token evidence and never run KQL, prove license/data-source visibility or create a hunting job. Application/shared-scope configuration, qualification and retained-scope revocation are Admin-only. Application mode requires explicit Admin opt-in, shared-scope approval and application qualification; there is no automatic fallback. See [docs/defender-agent365-hunting.md](docs/defender-agent365-hunting.md) for source/projection allowlists, dynamic-detail limitations, job bounds and the `rootSpanObserved` boundary.

## Package Feed And Export

Dependency, test, operator and browser build stages select the approved **`https://packagefeedproxy.microsoft.io/npm/`** registry automatically. Runtime receives no registry credentials. Stock Node maintenance containers must pass that setting explicitly:

```bash
docker run --rm -e NPM_CONFIG_REGISTRY=https://packagefeedproxy.microsoft.io/npm/ \
  --mount "type=bind,source=$PWD,target=/app" -w /app node:24-bookworm-slim \
  npm install --package-lock-only --ignore-scripts
```

When feed authentication is required, use company onboarding and the optional BuildKit `--secret "id=npmrc,src=$HOME/.npmrc"` supported by install/prune stages. Never put credentials in build arguments or disable TLS/Defender. This is npm registry configuration for this project, not a Docker-wide network policy or a redirect for image/OS downloads.

```bash
docker build --platform linux/amd64 --target export --output type=local,dest=artifacts .
docker run --rm --network agent-control_default \
  --mount "type=bind,source=$PWD/artifacts,target=/evidence,readonly" \
  agent-control-operator:local backend/scripts/package-smoke.ts \
```

[Dockerfile](Dockerfile) uses Node 24, compiles both workspaces, and exports `artifacts/agent-control-linux-x64.zip` from the same release tree. Linux/x64 checks reject an ARM-target export. The ZIP starts with `npm start` (one `node backend/dist/server.js` process), includes production dependencies and built assets, and excludes tests, operator scripts, SQLite data and local credentials. API/auth routing precedes static fallback; immutable hashed assets and no-store HTML have separate caching.

## Production Boundary

Production has one code path: [deploy-azure.ps1](deploy-azure.ps1), the [approved-target contract](infra/production-target.example.json), and [Bicep](infra/main.bicep). It deploys the same tested Linux/x64 ZIP to one Linux B1 App Service and one PostgreSQL 17 Flexible Server (`Standard_B1ms`, 32 GiB, seven-day backups), using five versioned runtime references from an existing prepared vault, plus the optional sixth `TENANTS_JSON` registry reference. Legacy mode requires explicit accepted domains. The administrator database secret remains bootstrap-only. Resource deployment starts in maintenance and is stopped before bootstrap; opening follows contained smoke and human authentication evidence. Monitoring exports only redacted application console events plus aggregate metrics, never raw HTTP/IP/URL or PostgreSQL query/session logs; backup health requires an exact receipt-bound restore-point probe rather than the backup-storage cost metric. The script requires an exact target, dated itemized estimate, budget/change/maintenance approval and explicit Burstable POC risk acceptance; examples and mock receipts are not approval or cloud evidence. See [Azure deployment](docs/azure-production-deployment.md) and [disaster recovery](infra/disaster-recovery.md). The removed `deploy-production.ps1`/Static Web Apps path has no compatibility wrapper. No local-only Phase 12 work accessed Azure.
